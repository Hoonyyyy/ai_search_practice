상태: 설계 승인 대기 → 승인 시 구현 계획(plan) 작성

## 1. 배경과 목적

`rag_search`(ai_search_practice)는 후니가 혼자 개발 중이다. 혼자 하는 개발이
외로워서, **같이 일하는 팀 같은 느낌**을 주는 도구를 원한다. 동시에 후니는
"Claude가 코드를 다 짜주다 보니 내 코딩 실력·워크플로우 감각이 준다"고 느끼고,
**테스트와 보안은 직접 손으로 짜면서** 배우고 싶어 한다.

이 문서는 그 두 가지를 만족하는 최소 기능(Phase 1)을 정의한다.

### 성공 기준 (Phase 1)

- 픽셀 아트 사무실 화면에서 동료 4명 + 후니 아바타가 보이고, "회의 소집" 시
  동료들이 회의실로 걸어가 앉는다.
- 후니가 회의 주제를 입력하면 동료들이 각자 역할·성격에 맞게 순서대로 발언하고,
  발언이 말풍선 + 팀 채팅 로그에 실시간(SSE)으로 뜬다.
- 회의가 끝나면 요약과 **액션 아이템 카드**가 업무 보드에 자동으로 꽂힌다.
  카드에는 담당자(동료 닉네임 또는 **후니**)와 태그(test/security/feature/fix/spike)가 붙는다.
- 서버를 껐다 켜도 보드와 사무실 상태가 복구된다.
- **기존 `rag_search` 코드는 단 한 줄도 바뀌지 않는다.** `office/` 폴더와
  `feature/office` 브랜치만 지우면 흔적 없이 제거된다.

### 동료가 쓰는 코드의 범위 (Phase 1)

- 동료는 회의·채팅에서 **코드 조각을 직접 작성해 공유**한다. 예: Sophia 가
  "`_embed` 에 이 프리픽스를 붙이죠" 하며 5~15줄짜리 코드 블록을 붙인다.
- 그 코드 블록은 액션 아이템 카드에 `draft_snippet` 으로 첨부된다.
- 동료는 **레포의 실제 파일을 읽지도 수정하지도 않는다.** 스니펫은 공유 브리핑과
  일반 지식에 근거한 "제안"이며, 실제 반영은 후니 + Claude 페어 세션에서 한다.
- 카드 스키마에 `draft_snippet?: {lang, code}` 필드 추가.

### 비목표 (Phase 1에서 안 하는 것)

- 동료가 실제 레포 파일을 읽거나 수정하는 것 (Phase 2~3)
- 동료가 커밋·PR을 만드는 것 (Phase 4)
- 에디터/IDE 기능 — 실제 코딩은 Claude Code 세션에서 후니 + Claude가 페어로 한다
- 인증·멀티유저·배포 — 로컬 전용, `127.0.0.1` 단일 사용자

## 2. 작업 방식 (핵심 결정)

**Phase 1에서 사무실은 "가벼운 동반자"다.**

- 실제 페어코딩은 지금처럼 Claude Code 세션에서 후니 + Claude. 후니가 직접 타이핑,
  Claude는 스펙·체크리스트·리뷰 담당.
- 사무실 앱은 별도 프로세스로, **출근한 동료 / 스탠드업·회의 / 팀 채팅 / 업무 보드**를
  담당한다. 보드 카드가 "사무실에서 정한 일"과 "Claude Code 세션에서 하는 일"을
  잇는 다리 역할.
- 근거: (1) 이미 잘 도는 페어코딩 루프를 안 건드린다 (2) 빌드가 작아 언제든 삭제
  가능하다 (3) 사무실의 가치는 "혼자가 아닌 느낌 + 워크플로우 의식"이지 IDE가 아니다.

### 테스트·보안 분담

| 항목 | 후니 | Claude / 동료 |
|---|---|---|
| 테스트 | pytest 케이스 직접 작성 | 테스트 하네스 + 가짜 Groq 클라이언트 + 체크리스트 제공, 리뷰 |
| 보안 | `office/SECURITY.md` 위협모델 + 입력검증 코드 작성 | 위협면 정리 도움, 리뷰 |
| 그 외 구현 | 원하면 참여 | 기본 담당, 후니가 요청하면 위임 |

### 5.1 서버 (FastAPI, 포트 8899)

기존 `backend-ai` 패턴을 그대로 따른다: `pydantic-settings` 설정, SSE 스트리밍
(`data: {json}\n\n`), Groq 클라이언트 지연 import.

**정적 파일**: FastAPI 서버가 `office/web/` 를 `/` 에 마운트해 직접 서빙한다.
→ 웹과 API가 동일 오리진(`http://127.0.0.1:8899`)이라 CORS 설정 자체가 불필요하다.
웹 상태 갱신은 `/office/state` 를 ~1초 주기로 폴링(회의 중에는 SSE가 주 경로).

**엔드포인트**

| 메서드 | 경로 | 설명 |
|---|---|---|
| `GET` | `/health` | Groq 키 유효성 + 데이터 로드 상태 |
| `GET` | `/office/state` | 동료·후니 위치, 상태값, 현재 회의 ID |
| `POST` | `/office/summon` | 회의실로 소집 (상태 전이만, 대화는 별도) |
| `POST` | `/meeting` | body `{topic, rounds?}` → **SSE 스트림** |
| `GET` | `/meeting/{id}` | 저장된 회의 전체(재연결·재렌더용) |
| `GET` | `/board/cards` | 보드 카드 목록 |
| `POST` | `/board/cards` | 카드 수동 추가 |
| `PATCH` | `/board/cards/{id}` | 상태/담당자/태그 변경 (컬럼 이동) |

**회의 SSE 이벤트**

```
data: {"type":"start","meeting_id":"..."}
data: {"type":"turn","speaker":"Sophia","text":"...", "seq":1}
data: {"type":"turn","speaker":"Victoria","text":"...","seq":2}
...
data: {"type":"summary","text":"..."}
data: {"type":"cards","cards":[{"title":"...","assignee":"후니","tag":"test"}, ...]}
data: {"type":"done"}
data: {"type":"error","message":"..."}   # 실패 시. 부분 대화록은 이미 저장됨
```

### 5.2 회의 퍼실리테이터 (`meeting.py`)

- 입력: `topic`(후니), `rounds`(기본 2, 최대 3), 공유 브리핑(`context.assemble_brief()`)
- 진행: 라운드로빈. 한 라운드 = 4명이 순서대로 각 1발언. 각 발언 = Groq 1콜.
  - 프롬프트 = `[시스템: 페르소나 + 말투 + "회의 규칙(짧게, 역할에 충실, 후니에게
    존대)"] + [유저: 브리핑 + 지금까지의 대화록 + "다음은 당신 차례입니다"]`
  - 응답은 2~4문장으로 제한(`max_tokens` ~200).
- 종료: 전체 대화록 → Groq 1콜로 `{summary, action_items[]}` JSON 추출.
  - action_item = `{title, detail, assignee, tag, draft_snippet?}`.
    assignee 는 4 닉네임 또는 `후니`. tag ∈ {test, security, feature, fix, spike}.
    `draft_snippet` = `{lang, code}` — 회의 중 동료가 제시한 코드 초안이 있으면 첨부.
  - **test/security 태그 카드는 기본 담당자를 후니로 강제**(후니의 학습 목표 반영).
- 저장: `office/data/meetings/{id}.json` (topic, 시작시각, turns[], summary, cards[]).

### 5.3 공유 브리핑 (`context.py`) — 읽기 전용

`assemble_brief()` 가 매 회의 시작 시 조립:

1. 손으로 쓴 `office/context/brief.md` (RAG 프로젝트 개요·현재 이슈·용어)
2. `git log --oneline -20` (subprocess, `cwd=repo_root`, 읽기 전용)
3. 레포 디렉토리 트리 상위 2단계 (`os.walk` 깊이 제한, `office/`·`venv`·`node_modules`
   ·`.git` 제외)

절대 파일 내용을 읽지 않는다(그건 Phase 2). subprocess 는 `git` 만, 인자 고정.

### 5.4 웹 (픽셀 아트, 바닐라 JS + Canvas)

- 라이브러리 없이 Canvas 2D. 타일 32px, 사무실 한 화면(스크롤 없음) 목표.
- 요소: 책상 4개(각 동료 정위치) + 회의 테이블 + 후니 자리. 아바타는 4방향
  걷기 스프라이트(간단히 2프레임).
- 이동: `office/state` 의 목표 좌표로 격자 경유 tween(A* 없이 맨해튼 경로면 충분).
- 상태 배지: `자리에 있음` / `생각 중…`(점 애니메이션) / `말하는 중` / `회의 중` / `⚠️`
- 말풍선: `turn` 이벤트 오면 해당 아바타 위 3초 표시 + 채팅 패널에 영구 로그.
- 패널: 좌하단 팀 채팅(회의 로그), 우측 업무 보드(4열: 할 일 / 진행 중 / 리뷰 대기 / 완료).
  카드 드래그로 열 이동 → `PATCH /board/cards/{id}`.
- 상단: 회의 주제 입력창 + "회의 소집" 버튼.

## 6. 데이터 흐름 — 회의 한 판

1. 후니가 주제 입력 → "회의 소집" 클릭
2. `POST /office/summon` → 서버가 동료 상태를 `회의 중`, 목표 좌표를 회의 테이블로
   설정 → 저장. 웹은 폴링/이벤트로 좌표 받아 아바타를 걷게 함
3. 아바타 착석 후 `POST /meeting {topic}` → SSE 오픈
4. 서버: 브리핑 조립 → 라운드로빈. 각 발언마다 `type:"turn"` 스트림
   - 웹: 말풍선 + 채팅 로그, 발언자 배지 `말하는 중`
5. 종료 → `type:"summary"`, `type:"cards"` → 보드에 카드 삽입, 저장
6. `type:"done"` → 서버가 동료 상태를 `자리에 있음`, 목표 좌표를 각자 책상으로 → 복귀

## 7. 에러 처리

| 상황 | 처리 |
|---|---|
| Groq 호출 실패(발언/추출) | 1회 재시도(지수 백오프 ~1s). 재실패 시 `type:"error"` + 부분 대화록 저장. 웹은 해당 아바타 ⚠️ + "이어서 진행" 버튼(다음 발언자부터 재개) |
| Groq 키 없음/무효 | `起動` 시 `GET https://api.groq.com/.../models` 확인 실패 → `/health` 가 `degraded`. 웹 상단에 "office/.env 에 GROQ_API_KEY 설정" 배너, 회의 버튼 비활성 |
| 서버 재시작 | `board.json` / `office.json` 재로드. 진행 중이던 회의는 `meetings/{id}.json` 에 `status:"incomplete"` 로 남고 UI에서 "미완료"로 표시 |
| EventSource 끊김 | 웹 자동 재연결. 재연결 시 `GET /meeting/{id}` 로 현재까지 turns 재렌더(중복 방지 위해 `seq` 기준 머지) |
| 회의 동시 실행 요청 | 서버는 활성 회의 1개만 허용. 이미 있으면 409 + 기존 `meeting_id` 반환 |
| 잘못된 카드/회의 ID | ID는 서버 생성 UUID만 허용. 경로 파라미터를 파일 경로에 직접 쓰지 않음(딕셔너리 조회) |
