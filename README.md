# rag_search

PDF·TXT·MD 문서를 올리면 임베딩해 벡터 DB에 저장하고, 질문하면 관련 청크를 찾아 LLM이 근거 기반으로 답하는 **RAG 문서 검색 서비스**입니다.

### 🔗 [배포된 서비스 바로가기](https://ai-search-practice-bk4z.vercel.app)

> 무료 호스팅이라 **첫 접속 시 서버를 깨우는 데 1~2분** 걸릴 수 있습니다. 화면에 경과 시간이 표시되고,
> 깨어나면 목록과 대시보드가 자동으로 채워집니다. 그 뒤 검색은 2~4초입니다. (→ [스토리 7](#7-배포-후에야-드러난-것--안에서-부른-요청은-잠든-서버를-깨우지-못한다))

React → Spring Boot → Python FastAPI → OpenAI / Groq / Qdrant Cloud / Supabase 로 이어지는 마이크로서비스 구조입니다. 로컬에서는 `.env` 설정만으로 Ollama + 임베디드 Qdrant + H2 의 완전 로컬 스택으로도 동작합니다.

## 이 프로젝트에서 봐주셨으면 하는 것

기능을 나열하기보다, **문제를 어떻게 찾아내고 무엇을 근거로 결정했는지**를 남기려 했습니다.

### 1. 검색 응답 4,485ms → 53ms (85배)

검색이 느려서 단계별로 계측했더니 내부 합계는 2,077ms인데 바깥에서 재면 4,132ms였습니다. **설명되지 않는 2초가 두 군데** 있었고, 크기가 비슷해 같은 원인이라 보고 좁혀 들어갔습니다.

```
localhost  로 호출 : 2058ms, 2084ms, 2089ms
127.0.0.1  로 호출 :   39ms,   46ms,   37ms
연결 재사용 시      : 2091ms → 37ms → 38ms   (첫 연결만 느림)
```

Ollama와 FastAPI는 `127.0.0.1` 에만 바인딩돼 있는데 `localhost` 는 IPv6(`::1`)로 먼저 해석됩니다. **모든 요청이 IPv6 연결 실패를 2초씩 기다린 뒤 IPv4로 폴백**하고 있었습니다. 코드도 모델도 DB도 정상이었고, 주소 문자열 하나가 원인이었습니다.

### 2. RAG 품질을 숫자로 관리하는 평가 체계

"검색이 잘 되는 것 같다"를 없애고 싶어서 평가 하네스를 직접 만들었습니다. **검색 단계와 답변 단계를 분리해서 잽니다.**

| 층 | 지표 | 현재 |
|---|---|---|
| 검색 | Recall@4 / 문서 적중률 / MRR@4 | **83.3% / 100% / 0.722** |
| 답변 | 정확도 / 과잉 거절 / 환각 | **77.8% / 1 of 18 / 1 of 4** |

```bash
cd backend-ai
python evals/run_eval.py          # 검색 단계
python evals/run_answer_eval.py   # 답변 단계
python evals/reload_corpus.py     # 설정 바꾼 뒤 코퍼스 재적재
```

두 층을 나눠 잰 덕분에 **"맞는 문서를 가져오면서 그 안의 엉뚱한 청크를 고르는"** 실패 유형을 분리할 수 있었고, 그것이 청킹 개선으로 이어졌습니다.

### 3. 측정으로 뒤집은 결론들

| 처음 판단 | 측정 결과 | 어떻게 드러났나 |
|---|---|---|
| 청크 350이 최적 | **500이 더 나음** (MRR 0.688 → 0.854) | Recall이 100% 천장에 닿아 판단 불가였음. MRR 도입 후 재측정 |
| 다단 PDF엔 `setSortByPosition(false)` | **`true` 가 우세** (94.4% vs 77.8%) | 추출 텍스트를 눈으로 본 인상이었음. 끝까지 재보니 반대 |
| 업로드 시간의 97.9%가 임베딩 | 맞지만 **그중 20%는 IPv6 대기** | 계측을 한 단계 더 쪼갠 뒤 드러남 |
| 클라우드 임베딩은 한국어에 약함 | **모델 나름** (Recall 38.9% vs 83.3%) | 모델 하나만 재고 결론 낼 뻔했음 |

세 번 모두 **측정 도구를 개선하자 앞선 결론이 뒤집혔습니다.**

### 4. top_k를 늘리면 검색은 완벽해지고 답변은 무너진다

| top_k | Recall | MRR | 답변 정확도 | 과잉 거절 | 환각 |
|---|---|---|---|---|---|
| **4** | 94.4% | 0.815 | **72.2%** | 2/18 | **1/4 (25%)** |
| 8 | 94.4% | 0.815 | 72.2% | 1/18 | 1/4 (25%) |
| 10 | **100%** | 0.820 | 44.4% | **0/18** | **4/4 (100%)** |

`top_k=10` 은 **검색 지표가 전부 최고점**입니다. 검색만 재는 시스템이었다면 "완벽하게 개선했다"고 결론 냈을 것입니다. 그런데 답이 없는 질문 4개에 **전부 답을 지어냈습니다.**

후보가 많아지면 LLM 앞에 그럴듯해 보이는 조각이 늘 하나쯤 놓이고, "근거가 없으면 거절하라"는 규칙이 발동할 기회를 잃습니다. **거절 능력과 검색 범위는 반비례합니다.**

검색 실패는 "모르겠습니다"로 끝나지만 환각은 사용자를 틀린 행동으로 이끕니다. 그래서 `top_k = 4` 를 유지했습니다.

### 5. 두 저장소 사이 정합성 — 예방·감지·회복을 분리

문서 메타데이터는 H2에, 벡터는 Qdrant에 저장됩니다. 업로드가 중간에 실패하면 **주인 없는 벡터**가 남고, 검색은 컬렉션 전체를 대상으로 하므로 삭제된 문서가 계속 답변을 오염시킵니다. (실측: Qdrant 2건 vs H2 0건)

- **예방** — 실패 시 방금 저장한 벡터를 되돌리는 보상 트랜잭션. 원래 예외는 그대로 전파
- **감지** — 기동 직후 정합성 점검. **경고만** 남기고 자동 삭제하지 않음
- **회복** — `GET /api/documents/leftovers` (조회) / `POST /api/documents/cleanup` (삭제)

삭제는 되돌릴 수 없으므로 감지와 실행을 분리했습니다. 동작 검증은 **결함을 주입해** 실패 경로를 강제로 태우고, 정리 후 원래 예외가 살아서 전파되는 것까지 로그로 확인했습니다.

### 6. 임베딩 모델 3종 비교 — 품질 11%p 를 배포 가능성과 맞바꾼 결정

같은 코퍼스·같은 청킹·같은 평가셋에서 **임베딩 모델만** 바꿔 끝까지 쟀습니다.

| | bge-m3 (로컬) | 3-small | **3-large (채택)** |
|---|---|---|---|
| Recall@4 | **94.4%** | 38.9% | 83.3% |
| MRR@4 | **0.815** | 0.361 | 0.722 |
| 답변 정확도 | 72.2% | — | **77.8%** |
| 업로드(122청크) | 83.6초 | 4.7초 | **6.8초** |
| 무료 배포 | **불가능** (모델 2GB) | 가능 | **가능** |

`3-small` 만 재고 멈췄다면 **"클라우드 임베딩은 한국어에 못 쓴다"**고 적었을 것입니다.
실패 목록을 보니 이력서 질문에 노트북 설명서만 가져오고 있었고(이력서는 136청크 중 14개),
모델을 하나 더 재자 같은 질문들이 전부 통과했습니다. **표본 하나로 일반화하지 않습니다.**

그리고 v4.11 에서 **"BM25 를 붙여도 해결되지 않는다"**고 분석했던 유일한 검색 실패
(`그만둔 이유` → `계약만료`)가 **1등으로 잡혔습니다.** 어휘 격차는 검색 기법이 아니라
**임베딩의 의미 표현력** 문제였습니다. 하이브리드 검색을 먼저 만들었다면 풀리지 않았을 것입니다.

품질만 보면 `bge-m3` 가 낫습니다. 그럼에도 클라우드를 택한 것은 **`bge-m3` 로는 배포할 수 없기
때문**입니다(모델 2GB, 무료 티어 512MB — v3.4 의 OOM 이 정확히 이 벽이었습니다).
**아무도 접속할 수 없는 94.4% 보다 접속 가능한 83.3% 가 낫다**고 판단했습니다.
로컬 개발은 `.env` 한 줄로 `bge-m3` 를 그대로 씁니다.

### 7. 배포 후에야 드러난 것 — "안에서 부른 요청은 잠든 서버를 깨우지 못한다"

무료 호스팅은 15분 동안 요청이 없으면 서버를 재웁니다. 서비스가 둘(Spring, FastAPI)이라
각각 깨어나야 하고, 그동안 화면은 아무 안내 없이 로딩만 돕니다. **첫 검색을 재보니 153.7초**였습니다.

깨우는 안내 배너를 붙여 해결했다고 생각했는데, 배너가 사라진 **직후의 검색이 102초** 걸렸습니다.
로그의 시각을 맞춰보니 원인이 드러났습니다.

    14:43:45  Spring 기동 → 정합성 점검이 FastAPI 호출 → 즉시 502
    14:45:45  검색 요청 → Spring 이 5초 간격으로 재시도 1/30 … 13/30 (70초, 전부 즉시 502)
    14:46:51  (원인 확인용으로) 바깥에서 FastAPI 를 직접 호출
    14:47:16  FastAPI 기동 — 바깥 호출 25초 뒤
    14:47:25  답변 도착 (102초)

Spring 은 3분 30초 동안 FastAPI 를 불렀지만 **한 번도 깨우지 못했습니다.** 호스팅 내부에서
공개 주소로 부르면 "자고 있다"는 502만 돌아오고, 바깥(브라우저·외부 크론)에서 부를 때만
요청이 보류되며 서버가 깨어납니다. 재시도를 30번까지 늘려도 해결되지 않는 종류의 문제였습니다.

**고침** — 깨우는 주체를 브라우저로 옮겼습니다. 페이지를 열면 Spring 과 FastAPI 를
**동시에** 두드리고(`Promise.all`), 검색·업로드 직전에도 한 번 두드립니다.
순차로 깨우면 최악 "2분 + 2분"이던 것이 병렬로 **2분**이 되고, 배너가 사라지면 검색이 바로 됩니다.

| | 수정 전 | 수정 후 |
|---|---|---|
| FastAPI 를 깨우는 주체 | 없음 (Spring 502 × 13회) | 브라우저가 페이지 열 때 |
| 배너 후 첫 검색 | 102초 | 약 5초 |
| 운영 실측(둘 다 잠든 상태) | — | Spring 2분 / FastAPI 22초 **병렬** |

이 과정에서 **측정 행위가 결과를 바꾼** 사례도 남았습니다. 원인을 보려고 보낸 확인 요청이
FastAPI 를 깨워버려서, "바깥 호출이 깨웠다"와 "원래 100초 걸린다"는 두 해석이 **같은 시각표**를
만들었습니다. Spring 의 재시도 로그(13회 전부 502)가 둘을 갈랐습니다.

### 8. 업로드 한도 200MB — 근거 없는 숫자를 측정으로 바꿨다

파일 한도는 200MB, 업로드 스레드는 제한 없음(`newCachedThreadPool`), 서버 메모리는 512MB였습니다.
어느 값도 측정에서 나온 것이 아니었습니다.

**운영과 같은 조건을 먼저 만들었습니다.** 힙을 운영과 동일하게 제한하고(`-Xmx358m`, 512MB의 70%),
AI 서비스는 응답 시간만 운영과 비슷하게 흉내 낸 가짜 서버로 대체해 **Spring 의 메모리만** 분리했습니다.
0.5초마다 힙 사용량을 기록했습니다.

| PDF 크기 | 1개 | 2개 동시 | 3개 동시 |
|---|---|---|---|
| 3.5MB | 117MB (33%) | 139MB (39%) | – |
| **10MB** | 104MB (29%) | 133MB (37%) | **162MB (45%)** |
| 20MB | 162MB (45%) | 218MB (61%) | 288MB (80%) |
| 67MB | 342MB (95%) | | |
| 100MB | 345MB (96%), **39초** | | |

PDF 텍스트 추출은 **파일 크기의 약 5~6배** 힙을 씁니다. 한도의 3분의 1인 67MB 하나로 이미 95%,
100MB 하나는 96%에 39초가 걸렸습니다(정상 8초). 터지진 않지만 그 시간 동안 **다른 사용자의 검색도
같이 느려집니다.** 200MB 는 한 번도 버틸 수 없는 값이었습니다.

**결정** — 파일당 10MB, 동시 업로드 3개(나머지는 대기열). 최악의 경우 힙 45%로, 검색 몫이 남습니다.
업로드 전용 스레드풀을 두어 **업로드가 밀려도 검색은 줄 서지 않게** 분리했습니다(벌크헤드).

**측정 도구를 세 번 의심해야 했습니다.** 첫 측정은 힙 제한이 적용되지 않아(빌드 도구 설정이
명령줄 값을 덮어씀) 8GB 힙에서 재고 있었고, 가짜 서버가 요청 본문을 읽지 못해 큰 파일이 실패로
기록됐으며, IDE 가 만든 클래스 파일 때문에 컴파일되지 않는 코드가 "빌드 성공"으로 보고됐습니다.
**첫 줄에 힙 최대값을 찍게 해둔 덕분에** 첫 번째를 잡았고, 나머지는 결과가 이상해서 도구를 뒤졌습니다.

그리고 이 작업의 테스트가 버그 셋을 더 잡았습니다.

- **경쟁 조건** — "대기 중" 안내를 스레드 활성 개수로 판단했더니, 동시에 들어온 요청들이
  **아직 출발 전인 스레드**를 세어 아무도 안내를 받지 못했습니다. 카운터를 직접 증감하도록 고쳤습니다.
- **무한 로딩** — 크기 초과 시 기본 응답(413)은 본문이 비어 있어, 화면이 "업로드 중"에서
  영원히 멈췄습니다. 한도를 200MB → 10MB 로 내리는 순간 운영에서 바로 터졌을 문제입니다.
- **에러 응답에 CORS 헤더 누락** — 413 에 사유를 담았는데도 브라우저는 "네트워크 오류"로 처리했습니다.
  CORS 를 컨트롤러 이후가 아니라 **필터로 옮겨** 모든 응답에 붙게 했습니다. 터미널 테스트는
  출처(Origin)를 붙이지 않아 통과했고, 브라우저로 확인하자 드러났습니다.

## AI 와 일한 방식

이 프로젝트는 AI(Claude Code)와 페어로 작업했습니다. 커밋에도 그대로 남아 있습니다.
드러내는 쪽을 택한 이유는, **결과물보다 AI 의 출력을 어떻게 검증했는지가 이 프로젝트의 내용**이기 때문입니다.

- **제안을 반박했습니다.** "업로드 중복을 파일 해시로 막자"는 제안을 받았지만, 실제 문제는
  *다른* 파일을 연달아 올리는 경우였습니다. 해시 중복 방지로는 막히지 않아 설계를 다시 세웠습니다.
- **도구의 보고를 믿지 않았습니다.** 측정 스크립트가 "67MB 업로드 실패"라고 보고했지만
  스택트레이스의 `Caused by` 가 소켓 예외를 가리켰습니다. 도구 버그였고, 결론을 폐기하고 다시 측정했습니다.
- **검증 환경을 의심했습니다.** 터미널에서 통과한 413 응답을 "브라우저에서도 해보자"고 다시 확인해
  CORS 헤더 누락을 찾았습니다.
- **순서를 바꿨습니다.** "기능을 만든 뒤 성능을 측정한다"는 계획에, 느리면 전부 다시 만들어야 하니
  **측정을 먼저** 하자고 순서를 바꿨습니다.
- **빌드 성공을 의심했습니다.** `mvn` 이 "BUILD SUCCESS"를 보고했지만 실제로는 컴파일을
  건너뛰고 있었습니다(IDE 가 만든 클래스 파일 때문). 강제로 컴파일하자 문법 오류가 나왔습니다.

공통점은 하나입니다. **"통과했다"는 보고를 근거로 삼지 않았습니다.** 도구도, AI 도,
스스로의 예상도 틀릴 수 있다고 보고 매번 측정으로 확인했습니다.
이 저장소의 `docs/changelog.md` 에는 틀린 결론과 그것을 어떻게 뒤집었는지가 함께 남아 있습니다.

## 구조

### 배포 구조 (현재 운영 중)

```
브라우저
   │  REST + SSE
   ▼
React  ─ Vercel 정적 호스팅
   │  REST + SSE
   ▼
Spring Boot  ─ Render (512MB)  ──→  Supabase Postgres (서울)   문서 메타 · 쿼리 로그
   │  내부 HTTP
   ▼
FastAPI      ─ Render (512MB)  ──┬→ Qdrant Cloud (US East)     벡터 저장 · 검색
                                 ├→ OpenAI  text-embedding-3-large (3072차원)
                                 └→ Groq    openai/gpt-oss-120b   답변 생성
```

무료 티어라 **512MB 제한과 15분 후 잠드는 특성**이 설계에 그대로 영향을 줬습니다.
업로드 한도(10MB × 동시 3개), 깨우는 순서, 임베딩 모델 선택이 모두 이 제약에서 나온 결정입니다.

### 로컬 스택 (완전 로컬, 외부 API 없이)

```
사용자 브라우저
    │  HTTP (REST + SSE)
    ▼
React 프론트엔드 (:3000)
    │  HTTP (REST + SSE)
    ▼
Spring Boot 메인 백엔드 (:8080)          ← 문서 메타·쿼리 로그·오케스트레이션
    │  내부 HTTP
    ├──────────────────────────────┐
    ▼                              ▼
Python AI 백엔드 (:8001)       H2 파일 DB
    │
    ├── Ollama (:11434)   임베딩 bge-m3 (1024차원) + LLM qwen2.5:3b
    └── Qdrant 임베디드    벡터 저장/검색 (backend-ai/data/qdrant)
```

**설계 원칙**: 프론트엔드는 Spring Boot하고만 통신합니다. Python AI 서비스는 Spring Boot가 내부적으로만 호출합니다.

업로드와 답변 생성은 모두 **SSE 스트리밍**입니다. 진행률과 토큰이 도착하는 대로 화면에 전달됩니다.

## 남은 과제

측정으로 확인했지만 아직 해결하지 못한 것들입니다.

**운영**

- **밤·주말 첫 접속 2분** — 평일 낮은 외부 크론으로 깨워두지만(무료 시간 한도 안에서),
  그 밖의 시간대는 여전히 대기가 필요합니다. 현재는 경과 시간이 보이는 안내 배너로 대응합니다.
- **힙 밖 메모리는 재지 않았다** — 업로드 측정은 힙만 봤습니다. 컨테이너 한도(512MB)는
  힙 + 클래스·스레드 메모리 합계로 판정되므로, 힙 96%인 상황에서 실제로는 호스팅이
  프로세스를 먼저 종료할 수 있습니다.
- **설계 원칙 이탈** — "AI 서비스는 Spring 이 내부적으로만 호출한다"는 원칙이 배포에서 깨졌습니다.
  무료 플랜에 내부 전용 서비스가 없어 AI 서비스가 공개됩니다. 공유 비밀키 헤더가 후보입니다.
- **문서가 모든 방문자에게 공유된다** — 로그인이 없어 누가 올린 문서든 모두가 검색할 수 있습니다.
  익명 세션 단위로 문서를 분리하고 1시간 뒤 자동 삭제하는 설계를 마쳤고, 구현이 남았습니다.

**품질**

- **근거는 있지만 해석이 틀린 환각** — "희망 근무 지역"을 물으면 과거 재직지를 답합니다.
  프롬프트 규칙("근거가 없으면 거절하라")으로는 막히지 않는 유형입니다.
- **평가셋 규모** — 18문항으로는 0.02 수준의 차이를 우연과 구분할 수 없습니다.
- **테스트 범위가 얕다** — 현재 테스트는 순수 함수·설정 수준 10개입니다.
  최근 고친 버그들(삭제 응답 코드, 재시도, 업로드 동시 제한)에 회귀 테스트를 추가하는 것이 다음 작업입니다.

**성능**

- **검색 시 원격 호출 2회** — 판단용 `count()` 가 로컬에선 0ms 였는데 원격 벡터 DB 에서는
  전체 지연의 30%입니다. 배포 환경에서 재측정 후 캐시 여부를 결정합니다.
