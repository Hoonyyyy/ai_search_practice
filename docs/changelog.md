## v4.27 — 익명 세션 (2/3): 새는 걸 먼저 찍고, 막고, 다시 찍었다

### 증거부터 남겼다
v4.26 으로 **목록은 나뉘었지만 검색은 그대로**였다. 고치기 전에 새 세션으로 화면을 찍었다.

| | 화면의 문서 목록 | 질문 "입사 1년 이상이면 연차가 며칠?" 의 답변 | 참고 문서 |
|---|---|---|---|
| **before** | 갤럭시북 1건 | "매년 **15일**의 연차가 부여됩니다. 반차는 09~13시, 14~18시" | **세션테스트.txt** + 갤럭시북 3건 |
| **after** | 갤럭시북 1건 | "제공된 문서에서 해당 정보를 찾을 수 없습니다." | 갤럭시북 **4건** |

`docs/images/session-leak-before.png`, `session-leak-after.png`.
**화면엔 없는 문서의 내용을 답변이 말하고 있었다** — 목록만 나누면 생기는 정확한 증상이다.
고친 뒤에는 고치기 전 상태가 이미 없으므로, **순서를 지켜야만 남는 기록**이다.

### 필터는 Qdrant 에게 넘겼다 (뽑고 거르지 않았다)
`top_k` 로 후보를 뽑은 뒤 파이썬에서 남의 청크를 걸러내는 방법은 틀렸다.
남의 청크가 상위 4개를 차지하면 **내 청크는 애초에 후보에 들지 못하고**, 걸러낸 뒤엔 0건이 된다.
그래서 `owner` 조건을 `query_points(query_filter=...)` 로 넘긴다. 원격 Qdrant 엔 `owner` keyword 인덱스도 만든다.

owner 가 없으면(= 아무 문서도 안 올린 방문자) `IsEmptyCondition` 으로 **payload 에 owner 가 비어 있는 청크**,
즉 예시 문서만 본다. 배포된 갤럭시북은 익명 세션 이전에 올라가 owner 키 자체가 없으므로 **여기에 그냥 들어맞는다.**

### `count` 가 `query` 보다 크게 새는 구멍이었다
`full_context_threshold` — 전체 청크가 12개 이하면 검색을 건너뛰고 **전부 답변 근거로** 넣는 지름길이 있다.
이 "전체"가 모든 사람의 청크를 세고 있었다. 방문자가 3청크짜리 문서 하나만 올린 상황에서
이 지름길이 타지면 **남의 문서가 통째로** 프롬프트에 들어간다.
`count(count_filter=...)`, `scroll(scroll_filter=...)` 까지 같은 조건을 넣어야 끝난다.

검증에서 이게 드러났다: 주인 세션으로 검색하니 **1건만** 왔다 — 그 세션의 문서는 청크가 1개뿐이라
`1 ≤ 12` 로 지름길을 탄 것. 필터 전이었다면 123개로 세어져 유사도 검색을 했을 것이다.

### 보이는 것과 검색되는 것을 한 규칙으로
검색 범위는 Spring 이 정한다(`DocumentService.resolveSearchOwner`) — **`listDocuments` 와 같은 규칙**이다.
내 문서가 있으면 내 것만, 없으면 예시 문서. 화면에 보이는 문서와 검색되는 문서가 다르면 사용자는 버그로 느낀다.
`owner` 는 null 일 수 있어 `Map.of` 대신 `HashMap` 을 쓴다(`Map.of` 는 null 값에 NPE).
FastAPI 쪽은 `owner: Optional[str]` 을 **기본값 없이** 둬서, 필드를 빠뜨리면 422 로 즉시 드러나게 했다.

### 평가 하네스가 조용히 깨져 있었다
익명 세션이 생기면서 `reload_corpus.py` 의 업로드는 세션 헤더가 없어 거절당하고,
`run_eval.py` / `run_answer_eval.py` 의 검색은 `owner` 가 없어 422 가 된다.
**포트폴리오의 핵심 도구가 조용히 죽어 있었다** — 평가를 안 돌리는 동안엔 아무도 모른다.

`evals/eval_session.py` 에 `EVAL_OWNER = "eval-harness"` 하나만 두고 세 스크립트가 가져다 쓴다.
세 곳에 각각 적으면 한 곳만 틀려도 **에러 없이 Recall 0%** 가 나오고, 그 숫자를 보고 임베딩 모델을 의심하게 된다.

- 문서 1개 제한(교체 확인), 1시간 만료 청소
- 회귀 테스트 — 지금 만든 분리는 **사람이 매번 시크릿 창을 열어 확인할 수 없는** 종류다

## v4.26 — 익명 세션 (1/3): 문서에 주인을 붙였다

### 문제 — 배포된 데모는 모두가 같은 서랍을 쓴다
누가 PDF 를 올리든 **모든 방문자에게 보이고, 누구나 지울 수 있다.**
면접관이 열었을 때 앞사람의 문서가 있으면 데모가 아니라 사고 현장처럼 보인다.
로그인을 붙이면 확실하지만, **면접관에게 회원가입을 시킬 수는 없다.**

### 결정 — 로그인이 아니라 익명 세션
브라우저가 `localStorage` 에 UUID 를 하나 만들고, 모든 요청에 `X-Session-Id` 헤더로 보낸다.
같은 PC·같은 브라우저의 모든 탭 = 한 세션. 시크릿 창·다른 브라우저 = 다른 세션.

**이건 인증이 아니다.** 터미널에서 `curl -H "X-Session-Id: 아무거나"` 로 위조된다(실제로 해봤다).
목적은 "남의 문서를 못 보게 지키는 것"이 아니라 **"방문자끼리 문서가 섞이지 않게 나누는 것"** 이다.
그래서 민감한 문서를 올리지 말라는 안내와 1시간 자동 삭제(3/3에서)가 함께 있어야 의미가 있다.

### 설계에서 고른 것들
| 갈림길 | 고른 쪽 | 이유 |
|---|---|---|
| `owner` 칼럼 NOT NULL vs **nullable** | nullable | 배포된 Supabase 에 이미 갤럭시북 1건이 있다. NOT NULL 이면 기존 행에 넣을 값이 없어 스키마 변경이 실패한다. nullable 로 두면 기존 행이 자동으로 `owner IS NULL` = **예시 문서**가 된다 — **마이그레이션 SQL 이 0줄** |
| 헤더 `required = true` vs **false** | false | keep-alive(cron-job.org)와 `pingServer()` 는 헤더를 못 붙인다. true 면 첫 준비 확인이 400 으로 죽어 화면이 영원히 "서버 깨우는 중"에 머문다. **읽기는 관대하게, 쓰기는 엄격하게** |
| 업로드에 세션이 없으면 | 거절 | 허용하면 `owner = NULL` 로 저장돼 **예시 문서가 돼버리고, 그러면 아무도 못 지운다** |
| 남의 문서 삭제 요청 | 403 아닌 **404** | 그 id 의 문서가 존재한다는 사실조차 알려줄 이유가 없다. 예시 문서만 403(이유를 알려야 하니까) |
| 삭제 결과 `boolean` | **enum 3값** | DELETED / NOT_FOUND / SAMPLE_PROTECTED. `switch` 식에 `default` 를 안 써서, 값이 늘면 컴파일이 깨져 여기를 고치라고 알려준다 |

### 확인하다가 잡은 것 네 개
**1. H2 엔 `owner` 가 들어갔는데 Qdrant 엔 안 들어갔다.**
코드를 고치고 **uvicorn 을 재시작하지 않아서** 옛 모듈이 계속 돌고 있었다(`--reload` 없이 띄웠다).
같은 업로드 한 번이 **두 저장소에 서로 다른 결과**를 남긴 셈 — 스토리 5의 "두 저장소를 한 트랜잭션으로 묶을 수 없다"가 눈앞에 나타났다.
검색 필터를 먼저 만들었다면 "문서를 올렸는데 검색이 0건"으로 보였을 테고, 필터·임베딩·top_k 를 다 의심했을 것이다.
**필터를 만들기 전에 "필터가 걸 대상이 실제로 저장됐는지"를 먼저 봤다.**

**2. 삭제 403 을 프론트가 삼키고 있었다.**
서버는 `403 {"message": "예시 문서는 삭제할 수 없습니다."}` 를 정확히 보냈는데
`await fetch(...)` 가 응답을 보지 않아 화면엔 아무 말 없이 문서가 다시 나타났다 — **버튼이 고장 난 것처럼 보이는 침묵 실패.**
v4.25 의 413 과 **같은 종류**다: 응답을 확인하지 않는 `await fetch(...)` 는 전부 잠재적 침묵 실패.

**3. 잔여 벡터가 실제로 생겼다.** 확인하려고 uvicorn 을 꺼둔 사이 삭제를 눌러서
H2 는 지워지고 벡터 삭제만 실패했다. v4.24 의 `/leftovers` → `/cleanup` 으로 1건 정리(`{"deleted":1}` → `count: 0`).
**"H2 먼저 → 벡터 나중" 순서가 옳았다는 증거** — 반대였다면 목록엔 보이는데 검색만 조용히 실패하는, 탐지 불가능한 상태가 됐다.

**4. 임베디드 Qdrant 는 한 프로세스만 연다.** payload 를 확인하려니
`Storage folder ... is already accessed by another instance`. 운영이 Qdrant Cloud 인 이유가
"클라우드가 좋아서"가 아니라 **여러 프로세스가 동시에 붙어야 해서** 라는 게 분명해졌다.

### 변경
| 파일 | 변경 |
|---|---|
| `api/session.ts` (신규) | `localStorage` 의 UUID 생성·보관, `sessionHeader()` |
| `api/documents.ts`, `api/search.ts` | 모든 요청에 헤더. 삭제 실패 시 서버 메시지로 `throw` |

| `domain/Document` | `owner` (nullable) |
| `repository/DocumentRepository` | `findAllByOwner…`, `findAllByOwnerIsNull…`. 전체 조회 메서드는 **삭제**(남겨두면 무심코 써서 분리가 깨진다) |

| `backend-ai/repositories/vector_repository.py` | payload 에 `owner`, 원격 Qdrant 에 `owner` keyword 인덱스 |

### 아직 안 된 것 (다음 PR)
- **검색이 아직 안 나뉜다** — Qdrant 서버측 `owner` 필터 + `full_context_threshold`(≤12청크면 전부 반환)의 세션별 처리. 지금은 남의 청크가 답변 근거로 섞인다
- **UI 가 오해를 부른다** — 예시 문서에 삭제 버튼이 그대로 있고(누르면 403), "업로드된 문서 (1)" 이라는 제목이 **2개 이상도 되는 것처럼** 읽힌다. `내 문서` / `예시 문서` 로 나누고 숫자를 뺄 것
- 문서 1개 제한(교체 확인), 1시간 만료 청소

## v4.25 — 업로드 한도를 숫자로 정했다: 10MB × 동시 3개

### 가설 — "동시 업로드가 쌓이면 512MB 서버가 터진다"
업로드 스레드는 `newCachedThreadPool`(제한 없음), 파일 한도는 200MB, 서버는 512MB.
운영에선 창을 닫아도 업로드가 12초 넘게 계속 돌아(v4.22 프록시 지연) "올리다 새로고침"이 겹칠 수 있다.
**고치기 전에 쟀다.**

### 측정 방법 — 운영과 같은 조건을 먼저 만들었다
- Spring 을 **운영 Dockerfile 과 같은 옵션**으로: `java -Xmx358m -XX:+UseSerialGC -Xss512k -jar` (358MB = 512MB × 70%)
- FastAPI 는 **가짜**: 약 7초 동안 진행률을 보내다 'stored' (운영 임베딩 7~18초 중 짧은 쪽). 비용 0원, Spring 메모리만 분리해서 본다
- N개 동시 업로드, `jstat` 로 0.5초마다 힙 사용량 → 피크. 끝나면 측정용 문서 기록만 지운다

### 측정 도구가 세 번 거짓말했다
| 도구의 거짓말 | 잡은 방법 |
|---|---|
| `mvn spring-boot:run -Dspring-boot.run.jvmArguments=-Xmx358m` → **힙 최대 7984MB** | 첫 줄에 힙 최대를 찍게 해 둠. `pom.xml` 의 `<jvmArguments>` 가 명령줄 값을 덮어썼다. `spring-boot:run` 은 `TieredStopAtLevel=1` 도 몰래 붙인다 → jar 를 `java -jar` 로 띄움 |
| 가짜 FastAPI 가 모든 요청을 **"None (0청크)"** 로 받음 → 67MB·100MB "실패" | 사용자가 찾아 준 `Caused by: SocketException`. RestTemplate 은 본문을 **chunked** 로 보내는데 가짜가 Content-Length 만 읽었다. 큰 본문은 Spring 이 보내는 도중 연결을 닫았다 |
| `mvn compile` → **BUILD SUCCESS**, 그런데 코드는 컴파일이 안 되는 상태 | VS Code 자바 확장이 에러가 있어도 `.class` 를 만들어, Maven 이 "up to date" 로 건너뜀. `.class` 를 치우고 강제 컴파일하자 진짜 에러가 나왔다 |

"67MB 에서 터진다"는 첫 결론은 두 번째 거짓말의 산물이었다. 도구를 고친 뒤 **청크 수(1211/2421/3631)까지 확인하고** 다시 쟀다.

### 결과 (힙 358MB)
| PDF | 1개 | 2개 동시 | 3개 동시 |
|---|---|---|---|
| 3.5MB | 117MB (33%) | 139MB (39%) | – |
| 10MB | 104MB (29%) | 133MB (37%) | **162MB (45%)** |
| 20MB | 162MB (45%) | 218MB (61%) | 288MB (80%) |
| 33.6MB | 222MB (62%) | | |
| 67MB | 342MB (95%) | | |
| 100MB | 345MB (96%), **39초** | | |

3.5MB 동시: 8개 179MB(50%) → 16개 292MB(82%) → 24개 316MB(88%, 11초).

- **가설은 절반만 맞았다.** 보통 크기 PDF 는 16개 동시에도 버틴다. 위험한 건 **큰 파일 하나** — PDF 추출이 파일 크기의 약 5~6배 힙을 쓴다
- 끝까지 터지지는 않았지만 90%를 넘으면 GC 에 시간을 다 써서 **100MB 하나가 39초**, 그동안 다른 사람의 검색도 느려진다
- **200MB 한도는 한 번도 버틸 수 없는 값**이었다
- 한계: 힙만 쟀다(힙 밖 메모리 약 100MB 는 가설). 로컬 CPU 가 빨라 운영보다 덜 겹친다

### 결정 — A안: 10MB × 동시 3개, 넘치면 줄 서기
최악(10MB 3개 동시) 162MB(45%). 검색·힙 밖 메모리 몫이 넉넉하다. 데모 문서(갤럭시북 3.5MB)는 충분히 들어간다.

| 파일 | 변경 |
|---|---|
| `application.yml` | `max-file-size: 10MB`, `max-request-size: 11MB` |
| `AppConfig` | `uploadExecutor` — `ThreadPoolExecutor(3, 3, …, LinkedBlockingQueue)`. 검색은 기존 `sseExecutor` 그대로 (**벌크헤드**: 업로드가 꽉 차도 검색은 줄 서지 않는다) |
| `DocumentService` | 업로드 전용 풀 사용. `AtomicInteger uploadsInFlight` 로 직접 세서 4번째부터 `stage: queued` "앞선 업로드가 끝나길 기다리는 중...". 본문은 `processUpload()` 로 분리, `finally` 에서 -1 |
| `UploadExceptionHandler` (신규) | `MaxUploadSizeExceededException` → `413 {"message": "<yml 값> 이하 파일만 올릴 수 있어요."}` |
| `CorsConfig` | `WebMvcConfigurer` → **`CorsFilter` (HIGHEST_PRECEDENCE)** |
| 프론트 | `MAX_UPLOAD_MB = 10` 한 곳에 정의. 업로드 칸에 주황 배지 "파일당 최대 10MB", 보내기 전에 크기 검사(파일명·크기 포함 문구), `!resp.ok` 처리, 에러를 빨간 박스로 |

### 테스트가 잡은 버그 세 개
**1. 경쟁 조건 — "대기 중"이 안 나갔다.** 처음엔 `getActiveCount() >= 3` 으로 판단했다.
6개가 거의 동시에 들어오면 스레드들이 **아직 출발 전이라** 활성 수가 0~2 → 아무도 "대기 중"을 못 받았다.
스레드 상태를 묻지 않고 `AtomicInteger` 로 **들어올 때 +1, 끝날 때(finally) -1** 로 바꿨다.

**2. 크기 초과 시 "업로드 중..." 에서 영원히 멈춤.** 기본 413 은 본문이 비어 있다.
프론트는 `data:` 줄만 기다리다 아무 콜백도 못 불렀다. 한도를 200→10MB 로 내리면 운영에서 바로 터졌을 문제다.

**3. 에러 응답에 CORS 헤더가 없었다.** 413 에 이유를 담았는데도 브라우저는 "업로드 중 오류가 발생했습니다".
`WebMvcConfigurer` CORS 는 **컨트롤러를 찾은 뒤** 헤더를 붙인다. 크기 초과는 그 전(multipart 해석)에 터진다.
터미널 테스트는 Origin 을 안 붙여서 통과했다 — **브라우저에서 해 보자는 제안**으로 찾았다. `CorsFilter` 로 맨 앞에서 붙인다.

#### 확인
| 테스트 | 결과 |
|---|---|
| 6.7MB × 6개 동시 | 3개씩 두 번(가짜 AI 도착 01:43:24 ×3, 01:43:32 ×3), 뒤 3개 첫 이벤트 `queued`, 힙 178MB(49%) |
| 업로드 칸 꽉 찬 중 검색 | 바로 처리 (풀 분리) |
| 끝난 뒤 3개 / `.docx` 실패 5번 뒤 3개 | 모두 대기 없이 시작 (성공·실패 경로 모두 -1) |
| CORS: GET·POST·OPTIONS·DELETE(404)·413 | 모두 허락 헤더 있음. 모르는 출처는 403 |
| 브라우저: 10.1MB | 보내기 전에 "⚠ 10MB 이하… (선택한 파일: 초과_10.1MB.pdf, 10.1MB)" |
| 브라우저: 프론트 한도를 잠깐 50MB 로 → 10.1MB | **서버 문구** "10MB 이하 파일만 올릴 수 있어요." (수정 전: "업로드 중 오류가 발생했습니다") |
| 브라우저: 6.7MB | 업로드 → 목록 → 삭제 |

한계: 한도를 **훨씬** 넘는 파일(예: 50MB)은 서버가 덜 받은 채 연결을 끊어 브라우저가 연결 에러로 볼 수 있다. 화면이 보내기 전에 막으므로 화면을 우회한 경우에만 생긴다.

사용자가 다시 올리면 **중복**이 생긴다(실제로 생겼고, 테스트 중복은 지웠다).
정합성은 지켜졌다(기록 1 + 벡터 122). 문제는 "사용자는 취소했다고 생각하는데 문서가 남는다"는 것이다.

처음엔 내용 해시로 중복을 막자고 했지만, **그건 같은 파일을 두 번 올릴 때만** 막는다.
"A 올리다 새로고침 → B 올리다 새로고침 → C" 는 그대로다. 그래서 방향을 바꿨다:
- 명시적 취소 (프론트가 doc_id 로 취소를 보내고, FastAPI 까지 전달)
- pending → 확인: 업로드가 끝나도 브라우저가 "완료 봤다"고 확인해야 확정. 확인이 없으면 자동 삭제
- 검색·목록은 확정된 문서만

두 저장소(Supabase + Qdrant)를 `@Transactional` 하나로 묶을 수 없으니 **분산 트랜잭션을 손으로 만드는 일**이다.

`emitter.complete()` 뒤 Tomcat 이 요청 스레드에서 `IOException: Broken pipe` 를 ERROR 로 찍는다. 우리 코드 밖이다.
Tomcat 로거를 통째로 끄면 진짜 서블릿 오류까지 숨으므로 **두기로 했다.**

**4. `listDocIds()` 에 502 재시도가 없다** → FastAPI 가 깨는 중이면 `/leftovers` 가 500
다른 AI 호출은 모두 502 를 재시도한다. 이것만 빠졌다.

**5. 운영의 PDF 추출이 느리다** — 7~18초 (로컬 약 1초). 약한 무료 CPU + 아직 데워지지 않은 JIT.

**6. 첫날 아침의 잔여 청크 32개** — 보상 로그 없이 남은 이유가 프록시 지연만으로는 다 설명되지 않는다. 미해결.

### 고침 — 없는 문서 삭제는 404
- `DocumentService.deleteDocument` 가 `boolean` 을 돌려준다. `existsById` 로 먼저 보고, 없으면 **벡터도 건드리지 않고** false
- `DocumentController` 가 false 를 `404 "문서를 찾을 수 없습니다."` 로 바꾼다. 서비스는 HTTP 를 모른다

기록이 없으면 벡터를 안 건드리는 것은 의도다. 약속은 "기록이 있으면 벡터도 완전하다"이고,
기록 없는 벡터(잔여 벡터)는 `/leftovers` + `/cleanup` 의 몫이다. 삭제 API 는 "문서"를 지운다.

`existsById` 와 `deleteById` 사이에는 틈이 있다. 동시에 두 번 지우면 둘 다 200 을 받을 수 있다.
결과가 "이미 지운 걸 한 번 더 성공이라 함"이라 해가 없어서, 지운 줄 수를 돌려받는 쿼리 대신 단순한 쪽을 골랐다.

프론트는 그대로다. 삭제 버튼은 응답과 상관없이 목록을 다시 불러온다.

#### 확인 (로컬)
| 요청 | 결과 |
|---|---|
| 없는 id 삭제 | **404** (수정 전 200) |
| 테스트 `.txt` 업로드 → 삭제 | **200**, 목록·벡터 모두 사라짐 |
| 같은 id 한 번 더 삭제 | **404** |

기존 문서 2개(기록 + 벡터)는 테스트 전후로 그대로였다.

## v4.21 — 잠든 서버를 기다리는 이유를 보여주고, 깨면 저절로 채운다

### 원인 — 한 번 물어보고, 실패해도 아무것도 안 했다
v4.20 의 keep-alive 는 평일 낮만 덮는다. 밤·주말 방문자는 여전히 잠든 서버를 만난다.
그런데 "느리다"보다 "고장 났다"로 보인 진짜 이유는 프론트에 있었다.

- 문서 목록(`useUpload.loadDocs`)과 대시보드(`MetricsDashboard.load`)는 `useEffect(..., [])` —
  **페이지를 열 때 딱 한 번**만 서버를 불렀다
- 실패해도 에러 표시도, 다시 시도도 없었다. 서버가 2분 뒤에 깨어나도 **화면은 계속 비어 있었다**
- 기다리는 동안 아무 안내도 없었다

### 고침 — 서버 상태를 App 에서 한 번 확인하고, 아래로 내려준다
| 파일 | 역할 |
|---|---|
| `api/server.ts` | `pingServer()` — `GET /api/documents` 가 성공하면 true. 네트워크 예외도 false 로 삼킨다 |
| `hooks/useServerStatus.ts` | `checking → waking → ready / failed`. 5초마다 다시 묻고, 1초마다 경과 시간을 센다 |
| `components/layout/ServerStatusBanner.tsx` | 깨우는 중(주황, 경과 시간) / 실패(빨강, 다시 시도). 그 외엔 `null` |
| `App.tsx` | 훅을 **한 번만** 부르고 `serverReady` 를 내려준다 |
| `SearchPanel`, `MetricsDashboard` | `useEffect(..., [])` → `useEffect(() => { if (serverReady) load(); }, [serverReady])` |

설계에서 고른 것들:
- **3초 안에 답하면 배너를 띄우지 않는다.** 깨어 있는 평일 낮에 배너가 깜빡이면 오히려 이상하다

- **훅은 App 에 둔다.** 탭을 바꾸면 대시보드는 사라졌다 다시 생긴다. 대시보드 안에 두면 탭을 누를 때마다 확인이 처음부터 돈다
- **4분이면 포기한다.** 실측 최악 2분 30초의 여유를 두었다. "다시 시도"는 새로고침이다
- `role="status"` / `role="alert"` — 스크린 리더가 배너를 읽는다

### 확인 — Spring 을 끈 채로 프론트를 켜서 잠든 서버를 흉내 냈다
| 경우 | 결과 |
|---|---|
| Spring 꺼짐 | 3초 뒤 주황 배너, 초시계가 1초마다 오름, 목록은 비어 있음 ✅ |

로컬은 연결이 **바로 거절**되고 5초마다 다시 묻는다. Render 는 요청을 **붙잡고 있다가 한 번에** 답한다.
코드는 두 경우를 모두 처리하지만, 후자는 운영에서 확인해야 한다.

### 남은 것

- `listDocuments()` 등 다른 api 함수는 여전히 `resp.ok` 를 확인하지 않는다

## v4.20 — 한가한 사이트는 고장 난 사이트처럼 보인다: 평일 낮 keep-alive

## v4.19 — 검색 취소: 걱정한 문제는 없었고, 다른 문제가 있었다

### 처음 걱정 — "창을 닫아도 LLM 이 계속 답을 만드나?"
검색은 읽기만 하므로 정합성 문제는 없다(쿼리 로그는 답변이 끝나야 저장된다). 남는 건 낭비다.
**고치기 전에 보이게 만들었다.** FastAPI LLM 라우터에 `[llm] 완료/중단 — N개 전송, Xms` 를 `finally` 로 찍었다.

### 측정 도구가 자기 버그를 먼저 보고했다
측정 코드에 `sent` 를 `setn` 으로 쓴 오타가 있었다. 문법 검사는 통과했다(파이썬은 이름을 실행 시 확인한다).
첫 조각에서 `UnboundLocalError` → FastAPI 가 스트림을 도중에 끊음 → Spring 은 `Premature EOF`.

그리고 **사용자 화면엔 "AI 서버가 잠에서 깨어나는 중이에요"** 가 나갔다. 서버는 깨어 있었고 코드가 고장 났다.
기다려도 소용없는 상황에서 기다리라고 안내한 것이다.

#### 원인 — 같은 예외, 다른 의미
`ResourceAccessException` 은 서로 다른 상황을 한 봉투에 담는다.

| 봉투 속 원인 | 의미 | 안내 |
|---|---|---|
| `ConnectException` | 연결 자체가 안 됨 — 자는 중 | 기다리면 된다 |
| `SocketTimeoutException` | 연결이 느림 — 깨는 중 | 기다리면 된다 |
| `IOException: Premature EOF` | **연결된 뒤 응답 도중 끊김 — 서버 고장** | **기다려도 안 된다** |

v4.17 의 결함 주입은 FastAPI 를 **아예 꺼서** 첫 줄만 시험했다. 세 번째는 FastAPI 가 켜져 있고
코드가 터져야 나오는 경우라, 이 오타가 아니었으면 찾지 못했다.
`getCause()` 로 봉투를 열어 분류하도록 바꿨다.

### 측정 결과 — 걱정한 문제는 거의 없었다
Groq 는 첫 글자 이후 **답변 전체를 0.4초** 만에 쏟아낸다. 끊긴 뒤 헛되이 생성하는 양은 무시할 수준이다.

### 대신 예상 못 한 문제 — 끊긴 생성기가 매달렸다
끊은 요청의 `[llm]` 줄이 **몇 분이 지나도 찍히지 않았다.** `finally` 가 실행되지 않았다는 것은
생성기가 끝나지도, 닫히지도 않고 `yield` 에서 멈춰 있다는 뜻이다.

서버를 끄자 그제야 찍혔다.
```
[llm] 중단 - 9개 전송, 181535ms
```
**181초 동안 Groq 연결을 쥔 채 매달려 있었다.** 요청이 없는 한가한 서버에서는 파이썬의 청소가 돌지 않아
서버가 꺼질 때까지 남는다. 창 닫기 한 번에 하나씩 쌓인다.

**측정 도구를 먼저 달지 않았다면** "낭비가 있나"만 고민하다 진짜 문제(자원을 놓지 않음)는 놓쳤을 것이다.

#### 고침 — v4.17 업로드 방식 + 한 줄
- 묶음마다 `request.is_disconnected()` 확인 후 중단
- `finally` 에서 **`events.close()`** — 청소를 기다리지 않고 생성기를 직접 닫아 Groq 연결을 놓는다.
  업로드 생성기는 쥔 것이 없어 멈추기만 하면 됐지만, LLM 생성기는 외부 연결을 쥐고 있다

| 끊은 시점 | 보낸 조각 | 닫힌 시간 |
|---|---|---|
| 수정 전 (5조각) | 9개 | **181,535ms** (서버 종료 시) |
| 1조각 | 2개 | 712ms |
| 5조각 | 6개 | 550ms |
| 30조각 | 31개 | 545ms |

끊는 시점과 상관없이 1조각만 더 보내고 즉시 닫힌다.

### 창 닫기가 ERROR 로 쌓였다 — 양치기 소년
창 닫기는 흔한 정상 행동인데 Spring 은 `ERROR 검색 처리 실패` + 스택트레이스로 남겼다.
이게 쌓이면 진짜 에러가 묻히고, 나중에 에러 알림을 붙이면 창 닫을 때마다 울린다.

#### Spring 의 도구를 쓰지 않은 이유
Spring 6.1 의 `DisconnectedClientHelper` 를 열어 판별 기준을 확인했다.
```
예외 이름 : ClientAbortException, AbortedException, EOFException, EofException
메시지    : "broken pipe", "connection reset by peer"
```
**메시지로도 판별하는 것이 문제다.** `connection reset by peer` 는 Spring 과 FastAPI 사이 연결이 끊길 때도 나온다.
운영(리눅스)에서 FastAPI 가 죽으면 **서버 고장을 "사용자가 떠남"으로 분류해 INFO 로 묻는다** —
막으려는 것의 정반대다. 게다가 이 PC 에서는 메시지가 한국어라 문구가 맞지도 않는다.

`ClientAbortException` 은 Tomcat 이 **브라우저로** 응답을 쓰다 실패할 때만 던진다. 모호함이 없다.
원인 사슬을 따라가며 이 타입만 찾는 `isClientGone()` 을 만들었다.

도구가 있다고 우리 문제에 맞는 것은 아니다 — v4.11 의 BM25 와 같은 교훈이다.

- 검색: 사용자가 떠났으면 `INFO`, 메시지도 보내지 않는다(받을 사람이 없다)
- 업로드: 로그 등급만 바꾼다. **벡터 정리(안쪽 catch)는 그대로 돈다**

#### 검증
| 상황 | 로그 | 화면 |
|---|---|---|
| 검색 도중 끊기 (×3) | `INFO 사용자가 연결을 끊어 검색을 중단` | — |
| 업로드 도중 끊기 | `WARN 잔여 벡터 정리 완료` + `INFO 업로드를 취소` | — (잔여 0) |
| **FastAPI 끄고 검색** | **`ERROR` + `Connection refused` 원문** | "깨어나는 중" |

마지막 줄이 가장 중요하다. **창 닫기는 조용해지고, 진짜 고장은 여전히 시끄럽다.**

### 타이밍 경주 — 괜찮은 쪽이다
답변이 0.4초면 끝나다 보니, 끊긴 뒤 Spring 이 쓰기 실패를 느끼기 **전에** 답변이 다 끝나는 경우가 있다.
그러면 끊긴 검색이 정상 완료로 저장된다. 낭비 0.4초에 자원도 매달리지 않고 정상 종료하므로 막지 않았다.

### 변경 사항
- `routers/llm.py` — async + 끊김 감지 + `events.close()` + `[llm]` 측정 로그
- `ErrorMessages` — `ResourceAccessException` 을 원인별로 분류, `isClientGone()` 추가
- `SearchService`, `DocumentService` — 사용자가 떠난 경우 `INFO`

## v4.18 — 삭제 순서를 뒤집어 "감지 못 하는 어긋남"을 없앴다

### 문제
삭제는 벡터 → 문서 기록 순서였다. 그 사이에서 실패하면(DB 커넥션 끊김, 프로세스 사망)
**"기록은 있는데 벡터가 없는"** 상태가 남는다. 목록엔 문서가 보이는데 검색은 안 된다.

그리고 v4.6 의 감지 장치(`/leftovers`)는 반대 방향 — **"벡터는 있는데 기록이 없는"** 쪽만 본다.
이 방향은 **감지할 방법이 없었다.** v4.14 에서 예고했던 바로 그 구멍이다.

### 실패를 막을 수 없다면, 실패가 남길 상태를 고른다
순서만 뒤집었다. **기록 → 벡터.**

| 순서 | 벡터 삭제 실패 시 | DB 삭제 실패 시 |
|---|---|---|
| 전: 벡터 → 기록 | 아무것도 안 바뀜 | **기록만 남음 — 감지 불가** |
| 후: 기록 → 벡터 | 잔여 벡터 — **감지·회복 가능** | 아무것도 안 바뀜 |

실패 확률은 같다. 달라진 것은 **실패가 남기는 흔적이 전부 "잡을 수 있는 종류"가 됐다**는 점이다.

### 업로드와 거울 대칭
```
업로드 : 벡터 저장 → 기록 저장   (기록이 마지막)
삭제   : 기록 삭제 → 벡터 삭제   (기록이 처음)
```
두 흐름이 같은 불변식을 지킨다.

> **문서 기록이 있으면, 그 벡터는 반드시 완전하다.**

기록은 "이 문서 준비 완료" 도장이다. 업로드는 다 끝난 뒤 마지막에 찍고, 삭제는 가장 먼저 지운다.
사용자가 목록에서 보는 문서는 언제나 검색이 되는 문서다. 어긋나더라도 잔여 벡터 쪽으로만 어긋나고,
그쪽은 감지·회복 장치가 맡는다.

### 벡터 삭제 실패는 삼킨다 — 그리고 그 대가
사용자가 원한 것은 "목록에서 없애줘"이고 그것은 첫 단계에서 이미 이뤄졌다. 여기서 에러를 던지면
사용자는 "삭제 실패"를 보는데, 새로고침하면 문서는 사라져 있고 다시 지울 방법도 없다. 경고 로그만 남긴다.

**대가:** 정리 전까지는 지운 문서의 청크가 검색 결과에 섞일 수 있다. 드문 경우라 감지·회복에 맡긴다.
검색 시 기록 없는 doc_id 를 걸러내면 이 대가도 없앨 수 있다(남은 과제).

### 검증
| 테스트 | 결과 |
|---|---|
| A. 정상 삭제 (둘 다 켜짐) | DB 없음, 벡터 없음 |
| B. FastAPI 를 끈 채 삭제 | 응답 "삭제 완료", DB 없음, 경고 로그 기록 |
| B 이후 FastAPI 재기동 | `/leftovers` 가 해당 doc_id 1건 감지 → `/cleanup` 1건 삭제 → 잔여 0 |

B 가 핵심이다. **벡터 삭제를 일부러 실패시켰고, 남은 흔적을 기존 감지 장치가 실제로 잡았다.**

### 로컬 환경 정리
로컬 H2 와 로컬 Qdrant 파일이 서로 다른 시점의 데이터라 어긋나 있었다(기록 없는 벡터 3건,
벡터 없는 기록 2건). 후자는 감지 장치가 보지 못하는 쪽이라 존재조차 드러나지 않았다.
`/cleanup` → `reload_corpus.py` 로 136청크, 잔여 0 상태로 맞췄다.

### 변경 사항
- `DocumentService.deleteDocument` — 기록 → 벡터 순서로, 벡터 삭제 실패는 경고 로그

## v4.17 — 에러는 로그에, 사용자에겐 한 문장 / 새로고침하면 진짜로 취소된다

배포 후 발견한 두 문제를 고쳤다. 둘 다 **로컬에서는 만날 수 없던** 문제다.

### 1. 예외 원문이 사용자 화면으로 나갔다
배포 첫날, 콜드 스타트 중 첫 질문에 **답변 대신 HTML 덩어리**가 쏟아졌다. 원인은 한 줄이었다.

```java
"content", "검색 중 오류가 발생했습니다: " + e.getMessage()
```

`HttpServerErrorException.getMessage()` 는 상대 서버의 응답 본문을 통째로 담는다. 호스팅이 돌려준 안내 페이지 HTML 이 그대로 화면에 나갔다.

HTML 만의 문제가 아니다. 예외 원문에는 **내부 서비스 주소, DB 호스트와 사용자명, SQL, OpenAI 키의 일부**가 들어갈 수 있다. 공격자에게 내부 구조를 알려주는 힌트다.

**새어 나가는 길은 셋이었다.**

| 위치 | 경로 |
|---|---|
| `SearchService` | `e.getMessage()` 를 사용자에게 |
| `DocumentService` | 라이브러리가 던진 `IllegalArgumentException` 메시지까지 사용자에게 |
| `AiServiceClient` | FastAPI 가 보낸 에러 이벤트(파이썬 예외 원문)를 **열어보지도 않고** 전달 |

#### 원칙 — 문은 하나다
브라우저가 대화하는 건 Spring 뿐이므로 Spring 이 유일한 검문소다. **원문은 로그에, 사용자에게는 이해하고 행동할 수 있는 한 문장만.**

- `ErrorMessages` 신설 — 사용자 메시지를 정하는 곳을 한 군데로 모았다
- `AiServiceClient` — FastAPI 에러를 전달하지 않고 예외로 던진다 → 위 한 곳을 거친다
- `InvalidUploadException` 신설 — "화면에 보여줘도 되는 문장"이라는 사실을 **타입으로** 표시했다.
  라이브러리 예외는 이 타입이 아니므로 절대 이 길로 나가지 않는다

#### "숨기기"만으로는 부족했다
처음 안은 `"검색 중 오류가 발생했습니다."` 로 바꾸는 것이었다. 사용자는 이유도, 할 일도 모른 채
한 번 해보고 떠난다. 원인이 "서버가 자고 있다"면 **기다리면 해결된다는 것을 알려줘야** 한다.

```
❌ 검색 중 오류가 발생했습니다: <html>...        (전 — 내부 정보 노출)
❌ 검색 중 오류가 발생했습니다.                  (숨기기만 — 사용자가 떠남)
✅ AI 서버가 잠에서 깨어나는 중이에요. 30초-1분 뒤 다시 질문해주세요.
```

연결 거부·타임아웃(`ResourceAccessException`)과 502/503/504 를 "깨어나는 중"으로 분류한다.

#### 던지는 예외 타입이 사용자가 보는 문장을 결정한다
`AiServiceClient` 에서 FastAPI 에러를 `IllegalStateException` 으로 던진다. `IOException` 을 던지면
`RestTemplate` 이 `ResourceAccessException` 으로 포장하고, 그러면 **서버가 멀쩡한데도
"깨어나는 중"이라는 거짓 안내**가 나간다.

#### 틀린 안내는 안내 없음보다 나쁘다
작업 중 `IllegalArgumentException` catch 를 잘못 고쳐 `"PDF, TXT, MD 파일만 지원합니다."` 가
`"일시적인 문제... 다시 시도해 주세요"` 로 바뀐 적이 있다. `.docx` 를 올린 사용자는
**절대 성공할 수 없는 행동**(재시도)을 반복하게 된다. 되돌렸다.

#### 검증 — 결함 주입
FastAPI 를 끈 채 검색·업로드를 보냈다. 사용자에겐 안내 문장만, 로그에는
`I/O error on POST request for "http://127.0.0.1:8001/..."` 원문이 남았다.
**어제까지는 이 내부 주소가 화면에 나갔을 것이다.** `.docx` 는 여전히 형식 안내를 받는다.

코드를 고칠 때마다 **파일 수정 시각과 JVM 기동 시각을 비교**했다. 같은 결과가 나와도
옛 JVM 이 옛 코드로 답한 것일 수 있기 때문이다.

### 2. 업로드 중 새로고침하면 잔여 벡터가 남았다
운영 Qdrant 에 **갤럭시북 32청크(122 중 2묶음)** 가 주인 없이 남아 있었다. 업로드 도중 새로고침한 흔적이었다.
재시작·OOM 기록은 없었다.

#### 재현
로컬에서 `curl -m 3` 으로 업로드 3초 뒤 연결을 끊었다(= 새로고침).

```
15:26:24.5  Spring: 진행률 전송 실패 → 보상 트랜잭션 → "잔여 벡터 정리 완료"
+2.1초      잔여 벡터 등장
```

**보상 트랜잭션은 돌았지만 너무 일찍 돌았다.** Spring 이 끊겨도 FastAPI 는 모른 채 남은 묶음을
계속 저장했고, 정리 **이후에** 저장된 벡터는 아무도 지우지 않았다. **경쟁 상태**다.
v4.6 에서 보상 트랜잭션을 만들 때 "실패하면 FastAPI 도 같이 멈춘다"고 암묵적으로 가정했는데 틀렸다.

#### 먼저 고려했다 기각한 안 — "끊겨도 업로드는 끝까지"
브라우저 연결은 진행률 창구일 뿐이니 끊겨도 작업을 계속하자는 안이었다. **기각했다.**
A 를 올리다 새로고침하고 A 를 다시 올리면 **A 가 두 개**가 된다 — 방금 운영에서 치운 그 중복을
일부러 만드는 셈이다. 새로고침은 "취소하고 다시"라는 뜻이다.

#### 쓰는 쪽이 치운다
Spring 은 FastAPI 가 **언제 쓰기를 멈췄는지 알 수 없다.** 서로 다른 프로세스다. FastAPI 자신은 안다.

- 묶음 하나를 저장한 뒤, 다음 묶음 전에 `request.is_disconnected()` 확인 → 멈춤
- `finally` 에서 끝까지 못 간 모든 경우(끊김, 예외)에 **직접** 삭제. OpenAI 에러로 실패해도 치워진다
- 정리는 `await` 없이 호출한다. 취소가 진행 중이면 `await` 지점에서 또 끊겨 정리가 중간에 멈출 수 있다
- Spring 의 보상 트랜잭션은 그대로 둔다(이중 안전장치). 이미 지운 것을 또 지우는 것은 무해하다

#### 검증 — 끊는 시점을 바꿔 세 번
경쟁 상태는 타이밍에 따라 나타나기도 안 나타나기도 하므로 한 번 통과로 판단하지 않았다.

| 끊은 시점 | FastAPI | 치운 쪽 | 결과 |
|---|---|---|---|
| 3초 | `[embed] 중단 → 정리` | FastAPI (+ Spring) | DB·벡터 모두 없음 |
| 5초 | `[embed] 중단 → 정리` | FastAPI (+ Spring) | DB·벡터 모두 없음 |
| 7초 | 122청크 **완료** 후 끊김 | Spring 보상 트랜잭션 | DB·벡터 모두 없음 |

7초는 임베딩이 끝난 **뒤** 끊겨 FastAPI 가 치울 것이 없었다. 쓰기가 끝났으니 Spring 의 정리와
경쟁할 상대도 없다. **두 겹이 서로 다른 경우를 맡는다** — 쓰는 도중은 FastAPI, 쓰기는 끝났는데
마무리를 못 한 경우는 Spring.

#### 실패 지점은 단계가 아니라 "저장된 상태"로 센다
추출 중, 청킹 중, 임베딩 N묶음째... 단계를 세면 끝이 없다. 데이터가 어긋나는 것은 **무언가를
저장했을 때뿐**이다. 업로드는 벡터 → 문서 기록 순으로 딱 두 번 저장한다.

| 끊긴 순간 저장된 것 | 처리 |
|---|---|
| 없음 (수신·추출·청킹) | 지울 것 없음 |
| 벡터 일부 | FastAPI 가 멈추고 치움 |
| 벡터 전부, 기록 없음 | Spring 보상 트랜잭션 |
| 벡터 + 기록 | 서로 맞음 — 업로드 성공 |
| 프로세스 사망 | 예방 불가 → 감지(`/leftovers`) + 회복(`/cleanup`) |

벡터를 먼저, 기록을 나중에 저장하므로 업로드 중에는 "기록은 있는데 벡터가 없는" 상태가 생기지 않는다.

#### 운영에서는 예방이 뚫렸고 감지가 잡았다
오늘 운영의 32청크는 v4.6 의 감지(`/leftovers`)로 발견하고 회복(`/cleanup`)으로 치웠다.
예방·감지·회복을 분리한 이유가 운영에서 증명됐다.

### 확인한 것 — 사고가 아니었다
운영 Supabase·Qdrant 가 **둘 다** 비어 있어 긴장했으나, 둘이 **똑같이** 비었다는 점에서 인프라 장애가
아니라 앱의 삭제 API 가 불린 것으로 좁혔다. 본인이 전날 삭제한 것으로 확인됐다.

### 운영 원칙 추가
- **공개 데모에는 갤럭시북 설명서만 올린다. 이력서는 올리지 않는다.** 인증이 없어 누구나
  "연락처가 뭐예요?"라고 물어 개인정보를 꺼낼 수 있다
- **로컬 `.env` 가 운영 Qdrant 를 가리키지 않게 했다.** 로컬에서 `/cleanup` 한 번이면
  운영 벡터가 지워질 수 있는 구조였다

## v4.16 — 배포 완료, 그리고 배포해야만 보이는 것들

**https://ai-search-practice-bk4z.vercel.app**

### 구성
```
Vercel (React)
   └→ Render (Spring Boot)  ─┬→ Render (FastAPI) ─┬→ Qdrant Cloud (N. Virginia)
                             │                    ├→ OpenAI 임베딩
                             │                    └→ Groq LLM
                             └→ Supabase Postgres (서울)
```
서버에 남은 것은 코드뿐이다. 데이터는 전부 외부에 있다.

### 배포 순서는 의존성이 정한다
서로가 서로의 주소를 필요로 하므로 한 바퀴 돌아야 한다.
```
FastAPI 배포 → URL → Spring 의 AI_SERVICE_URL
Spring 배포  → URL → 프론트의 REACT_APP_API_URL
프론트 배포  → URL → Spring 의 CORS_ALLOWED_ORIGINS
```

### 포트는 우리가 정하지 않는다
호스팅이 `PORT` 로 지정한다. 앱이 8080 을 고집하면 **서비스는 떠 있는데 요청이 닿지 않는다.**
로그에서 `Uvicorn running on http://0.0.0.0:10000` 과 `[io-10000-exec-1]` 을 확인해
환경변수가 실제로 먹었음을 검증했다.

Dockerfile 의 `CMD` 는 **셸 형식**이어야 한다. 대괄호(exec) 형식은 셸을 거치지 않아
`${PORT}` 가 문자열 그대로 전달된다.

### 기본값은 "혼자 쓴다"를 가정한다 — 커넥션 풀 초과
첫 배포가 기동 실패했다.
```
FATAL: (EMAXCONNSESSION) max clients reached in session mode
                         max clients are limited to pool_size: 15
```
HikariCP 기본 풀 크기는 10이다. Supabase 무료 티어의 동시 접속 한도는 15.
로컬 개발 인스턴스(10)와 Render 인스턴스(10)가 겹치자 넘어섰다.

5로 제한해 `로컬 5 + Render 5 + 재배포 중 겹침 5 = 15` 에 맞췄다.

v4.15 의 `count()` 와 같은 종류의 문제다. **실행 환경이 바뀌면 기본값의 적절함도 바뀐다.**
로컬 전용 DB 에서 10개는 아무것도 아니지만, 공유 무료 DB 에서는 한도의 3분의 2다.

### 배포 직후 발견 — 콜드 스타트가 에러를 답변으로 만든다
배포 후 첫 질문에 **148초가 걸리고 답변 대신 HTML 덩어리가 화면에 쏟아졌다.**

```
자고 있을 때 : 148초, HTML 응답
깨어 있을 때 :  2.1초, 정상 답변 150토큰
```

원인은 두 가지가 겹친 것이다.

1. **콜드 스타트** — Render 무료 플랜은 15분 무응답이면 잠든다. 서비스가 둘이라 각각 잠들고,
   최악의 경우 Spring 60초 + FastAPI 60초 = 2분이다. 실측 `/health` 응답이 21초였다.
2. **에러를 답변으로 내보내는 버그** — FastAPI 가 깨어나는 동안 Render 가 HTML 안내 페이지를
   응답했는데, **Spring 이 형식 검사 없이 그대로 사용자에게 스트리밍했다.**

2번이 더 나쁘다. "답변이 안 나온다"가 아니라 **"이상한 코드가 쏟아진다"** 이기 때문이다.
시끄럽게 실패하긴 했으나 엉뚱한 방향이었다.

**이것은 로컬에서는 절대 만날 수 없는 문제다.** 배포하지 않았다면 면접관이 링크를 눌렀을 때
처음 봤을 것이다.

### 설계 원칙 하나가 깨졌다 — 기록해둔다
"프론트엔드는 Spring 하고만 통신하고 FastAPI 는 내부 호출 전용" 이 원칙은 배포에서 깨졌다.
Render 무료 플랜에는 **내부 전용 서비스가 없어** FastAPI 가 인터넷에 공개된다.
데모로는 문제가 아니지만 의도한 구조는 아니다. 공유 비밀키 헤더 검사가 해법 후보다.

### 리전이 흩어져 있다
Supabase 만 서울이고 나머지는 미국 동부다. Qdrant 무료 티어에 아시아 리전이 없어
US 를 골랐고, 호스팅도 그에 맞춰 Virginia 로 했다.
Supabase 는 데이터가 적어 재생성 비용이 낮으므로 나중에 맞춘다.

### 남은 과제 (배포해서 알게 된 것)
1. Spring 이 AI 서비스 응답 형식을 검사하지 않고 그대로 흘린다 — 사용자용 메시지로 치환해야 한다
2. 첫 방문 대기 2분 — 프론트에 "서버를 깨우는 중" 안내와 진행 표시 필요
3. 배포 환경에서 검색 지연 재측정 — 서버와 Qdrant/OpenAI 가 같은 대륙이 됐으므로
   v4.15 의 `count()` 왕복이 여전히 문제인지 다시 재야 한다

## v4.14 — H2 → Supabase Postgres (프로필로 전환, 자바 코드 변경 0줄)

### 왜 바꿨나
H2 는 `backend-spring/data/ragsearch` 라는 **파일**이다. 무료 호스팅은 재배포할 때마다
디스크가 초기화되므로, 배포 상태에서는 코드 한 줄 고쳐 올릴 때마다 이렇게 된다.

```
문서 목록      → 사라짐
대시보드 이력  → 사라짐
Qdrant 벡터    → 남아 있음      ← 매 배포마다 잔여 벡터 발생
```

**DB 는 서버 밖에 있어야 한다.** 서버가 죽거나 재배포되어도 데이터는 별도로 남는다.
H2 는 애초에 운영 DB 가 아니라 테스트용이기도 하다.

### 환경변수 4개가 아니라 프로필을 쓴 이유
임베딩(v4.12)은 `EMBED_PROVIDER` 환경변수 하나로 전환했다. DB 는 다르게 했다.

DB 전환은 **URL·드라이버·계정·비밀번호 네 개가 함께** 바뀐다. 환경변수로 하면
URL 만 Postgres 로 바꾸고 드라이버를 안 바꾸는 **어중간한 상태**가 만들어질 수 있다.

프로필은 네 개가 한 덩어리로 움직인다. 절반만 바뀐 상태가 **애초에 불가능하다.**
"잘못된 상태를 표현할 수 없게 만든다"는 기준을 따랐다.

```
application.yml            기본 — H2 (로컬 개발은 그대로)
application-supabase.yml   SPRING_PROFILES_ACTIVE=supabase 로 켠다
```

비밀번호는 `${SUPABASE_DB_PASSWORD}` 로 **기본값 없이** 받는다. 환경변수가 없으면
기동 자체가 실패한다 — 파일에 적지 않기 위해서이고, 빠뜨렸을 때 조용히 넘어가지 않게 하려는 것이다.

### 자바 코드는 한 줄도 바뀌지 않았다
JPA 를 쓰고 있어 엔티티·레포지토리·서비스 모두 그대로다.
바뀐 것은 **의존성 하나(postgresql 드라이버)와 설정 파일 하나**뿐이다.
`ddl-auto: update` 가 엔티티를 보고 `documents` / `query_logs` 테이블을 SQL 없이 생성했다.

### 접속은 Session pooler 를 쓴다
Supabase 의 Direct connection 은 IPv6 주소를 준다. 이 PC 는 v4.7 에서
**IPv6 폴백 때문에 요청마다 2초를 잃던** 이력이 있다. Session pooler 는 IPv4 로 붙는다.
같은 함정을 두 번 밟지 않기 위한 선택이다.

### RLS — 안 쓰는 문을 닫았다
Supabase 는 `public` 스키마의 테이블을 REST API 로 자동 공개하며, RLS 가 꺼져 있으면
Table Editor 에 빨간 `Unrestricted` 배지가 붙는다.

우리는 Data API 를 쓰지 않는다(프론트엔드는 Spring 만 호출한다). 쓰지 않는 경로는 닫는다.

```sql
alter table documents  enable row level security;
alter table query_logs enable row level security;
```

정책을 하나도 만들지 않으면 전부 거부된다. 반면 Spring 은 테이블 **소유자**인
`postgres` 로 접속하므로 RLS 를 통과한다. 필요한 문만 열려 있는 상태가 된다.
`documents` 에는 이력서 파일명 같은 개인정보가 들어가므로 더 그렇다.

**적용 후 실제로 확인했다** — RLS 를 켠 뒤에도 `/api/documents/leftovers` 가 정상 응답했다.

### 전환 중 예고된 상황이 그대로 발생했다
DB 를 바꾼 직후 Postgres 는 문서 0건, Qdrant 는 벡터 136개였다.
**배포할 때마다 생길 것이라고 예측했던 잔여 벡터가 DB 전환에서 먼저 나타났다.**

v4.6 에서 만든 도구로 처리했다. 감지(`GET /leftovers`) → 정리(`POST /cleanup`) → 재적재.
정리하지 않고 재적재했다면 벡터가 272개가 되어 검색이 오염됐을 것이다.

**v4.6 에서 자동 삭제(A안) 대신 경고만(C안) 선택한 판단도 여기서 값을 했다.**
자동 삭제였다면 DB 를 바꾼 순간 Qdrant 컬렉션이 통째로 지워졌을 것이다.

### 검증
```
Postgres  documents  : 사람인_이력서 14청크 + Galaxybook 122청크
Qdrant    doc-ids    : 동일한 doc_id 2개
검색                 : 정답 청크 반환
query_logs           : 검색 1회 후 1건 기록
대시보드             : total_queries 1, avg 1508ms, tokens 1496
```

### 과거 쿼리 로그는 옮기지 않았다
H2 에 쌓인 이력에는 **IPv6 문제를 고치기 전의 4,485ms 기록**이 섞여 있다.
가져오면 평균이 계속 나빠 보인다. 새로 시작하는 쪽이 현재 성능을 정직하게 보여준다.
옛 기록은 H2 파일에 그대로 남아 있어 필요하면 꺼낼 수 있다.

### 변경 사항
- `pom.xml` — `org.postgresql:postgresql` (runtime) 추가, 버전은 부모 POM 관리에 맡김
- `application-supabase.yml` 신설 — datasource / dialect / h2 콘솔 비활성
- `application.yml` 무변경 — 로컬 기본값은 H2 유지

| 업로드(122청크) | 83.6초 | **4.7초** | 6.8초 |
| 검색 지연 | **64ms** | 278ms | 262ms |

### 하마터면 틀린 결론을 남길 뻔했다
`3-small` 만 재고 멈췄다면 **"클라우드 임베딩은 한국어에서 못 쓴다"** 고 적었을 것이다.
Recall 38.9% 는 그렇게 읽히기 충분한 숫자다.

실패 목록을 보니 **이력서 질문에 노트북 설명서 청크만 가져오고 있었다.**

```
자격증은 어떤 걸 가지고 있나요?  → Galaxybook × 4
다룰 줄 아는 기술이 뭔가요?      → Galaxybook × 4
```

이력서는 136청크 중 14개뿐이다. 한국어 구분력이 약하면 **수가 많은 쪽이 이긴다.**
모델을 하나 더 재자 같은 질문들이 전부 통과했다.
**표본 하나로 일반화하지 않는다** — v4.9 의 청크 350 오판과 같은 교훈이다.

### 계측 도구를 먼저 의심했다
Recall 은 38.9% 인데 문서 적중률은 83.3% 였다. **맞는 문서를 찾고도 청크를 틀리는** 패턴이라
배치 응답 순서가 섞였을 가능성을 먼저 확인했다. OpenAI 응답의 각 항목에는 `index` 가 붙어 있는데,
그것이 순서 보장이 필요하다는 뜻일 수 있기 때문이다.

```
응답 index 순서 : [0, 1, 2, 3, 4]   정렬돼 있음
질문 "갤럭시북 충전기 몇 와트야?" → 0.546 으로 정답이 1등
```

순서는 보존되고 있었다. **코드 버그가 아니라 실제 품질 차이**임을 확인한 뒤 결론으로 넘어갔다.

### 3년 된 실패 하나가 풀렸다
`계약만료` 검색 실패는 v4.11 에서 **"질문과 정답이 단어를 하나도 공유하지 않으므로
BM25 를 붙여도 해결되지 않는다"** 고 분석했던 유일한 Recall 실패다.

```
PASS    1     240ms  이전 직장을 그만둔 이유가 무엇인가요?
```

`3-large` 가 **1등으로** 잡았다. 어휘 격차는 검색 기법(하이브리드·재순위)의 문제가 아니라
**임베딩의 의미 표현력** 문제였다. 하이브리드 검색을 먼저 만들었다면 풀리지 않았을 것이다.

### 결정 — `text-embedding-3-large` 채택
품질만 보면 `bge-m3` 가 낫다(Recall +11.1%p, MRR +0.093, 검색 4배 빠름).
그럼에도 클라우드를 택한 이유는 **`bge-m3` 로는 배포할 수 없기 때문**이다.

| | 검색 품질 | 무료 배포 |
|---|---|---|
| bge-m3 (로컬) | Recall 94.4% | 불가능 — 모델 2GB, 무료 티어 512MB |
| 3-large (클라우드) | Recall 83.3% | 가능 — Ollama 서버 자체가 필요 없다 |

v3.4 의 OOM 이 정확히 이 벽이었다. **아무도 접속할 수 없는 94.4% 보다 접속 가능한 83.3% 가 낫다.**
답변 단계는 오히려 좋아졌고(72.2% → 77.8%, 과잉 거절 2 → 1건), 문서 적중률은 100% 그대로다.

로컬 개발은 `.env` 에서 `EMBED_PROVIDER=ollama` 로 계속 쓴다. v4.12 의 구조가 이를 위한 것이었다.

### 채점기의 한계 — 숫자 두 개는 믿지 않는다
1. **환각 2/4 는 과장이다.** `김치찌개` 케이스의 답변은 **빈 문자열**이었다. 지어낸 것이 아니라
   아무 말도 하지 않았는데, 채점기가 "거절 문구가 없으면 환각"으로 세었다.
   실제 환각은 `희망 근무 지역` 하나이며 이는 기준치와 동일하다. **빈 답변이 왜 나오는지는 별도 과제.**
2. **`몇년생` 오답은 정답이다.** 답변은 "1996년생입니다"였고 기대 문자열이 `29세` 라서 틀렸다고 나왔다.
   기준치에서는 이 질문이 과잉 거절이었으므로 **실제로는 개선**이다.

숫자는 추세용이고 실패 목록은 눈으로 읽어야 한다는 원칙을 다시 확인했다.

### 비용
전체 실험(재적재 3회 + 평가 수회) 비용은 **약 32원**이다.
`3-large` 기준 전체 재적재 1회 약 24원, 검색 1,000회 약 4원.
**임베딩 비용은 병목이 아니다.** 계정은 선불 $5, 자동 충전 해제 상태로 상한이 고정돼 있다.

### 변경 사항
- `.env.example` — 클라우드 임베딩 설정 견본 추가, 모델별 차원과 재적재 경고 명시
- 채택 설정: `EMBED_PROVIDER=openai`, `EMBED_CLOUD_MODEL=text-embedding-3-large`, `EMBED_DIM=3072`

### 남은 과제로 옮긴 것
- 답변이 빈 문자열로 나오는 케이스 (`김치찌개`) — 원인 미확인
- `run_answer_eval.py` 채점: 빈 답변을 환각과 구분하지 못함
- `reload_corpus.py` 가 업로드 청크 수를 `?` 로 출력 (v4.11 에서 고쳤으나 재발)

## v4.12 — 임베딩 provider 전환 준비 (측정은 아직)

### 배경
업로드 시간의 대부분이 CPU 임베딩이다(9청크에 6.9초). 소프트웨어로 줄일 수 없고,
배포 환경(무료 티어 512MB)에서는 더 나빠진다. v3.4 의 OOM 도 같은 원인이었다.

클라우드 임베딩 API 로 바꾸면 해결되지만, **바꾸는 것과 바꾸는 게 나은 것은 다른 문제다.**
여러 클라우드 모델이 한국어에서 `bge-m3` 보다 못하다. 그래서 이번에는
**전환 자체를 하지 않고, 전환할 수 있는 상태까지만** 만들었다.

### 변경 구조
임베딩 호출은 전부 `_embed()` 한 곳을 지난다(업로드·검색 공용). 여기만 갈라면 된다.

```
_embed()  ─┬─ provider == "ollama" ─→ _embed_ollama()
           └─ 그 외                 ─→ _embed_cloud()
```

기존 `llm_provider: ollama | groq` 패턴을 그대로 따라 `embed_provider` 를 추가했다.
**로컬 개발은 Ollama, 배포는 클라우드** 를 `.env` 만으로 전환한다.

### 순서를 나눈 이유
한 번에 만들지 않고 두 단계로 했다.

| 단계 | 성격 | 검증 |
|---|---|---|
| `_embed` → `_embed_ollama` 이름만 분리 | 동작 보존 변경 | 1024차원 그대로 나옴 |
| `_embed_cloud` 추가 + 분기 | 기능 추가 | 키 없이 전환하면 즉시 에러 |

**한 번에 하나만 바꾸면 실패했을 때 범인이 자동으로 특정된다.**
첫 단계에서 터지면 100% 이름 문제, 두 번째에서 터지면 100% 클라우드 코드 문제다.
IPv6 를 찾을 때 `localhost` 와 `127.0.0.1` 을 한 글자만 바꿔가며 쟀던 것과 같은 방법이다.

### 실패를 시끄럽게 만든 두 가지 판단
1. **`if provider == "ollama"` 로 분기** — `else` 가 클라우드다.
   `.env` 에 `ollma` 처럼 오타가 나면 클라우드로 가서 즉시 키 없음 에러가 난다.
   반대로 짰다면 조용히 로컬로 떨어져, 클라우드를 쓰는 줄 알고 실험했을 것이다.
2. **키가 없으면 요청 전에 `RuntimeError`** — `.env` 를 확인하라는 문구까지 담았다.

### 차원이 바뀌면 재적재가 필요하다
Qdrant 컬렉션은 생성 시 차원이 고정된다(`VectorParams(size=...)`).
`text-embedding-3-small` 은 1536차원이라 기존 1024차원 컬렉션에 넣을 수 없다.
**컬렉션 삭제 + 전체 재적재**가 필요하며, `evals/reload_corpus.py` 가 한 번에 처리한다.
이 경고는 `config.py` 주석에도 남겼다.

### 아직 하지 않은 것
**어떤 클라우드 모델을 쓸지 정하지 않았고, 채택 여부도 정하지 않았다.** API 키가 준비되면
후보별로 `.env` 교체 → 재적재 → `run_eval.py` 를 돌려 아래 기준치와 비교한다.

```
기준치 (bge-m3, chunk 500, top_k 4, 136청크)
검색 : Recall@4 94.4%   MRR@4 0.815   문서 적중 100%
답변 : 정확도 72.2%   과잉 거절 2/18   환각 1/4
```

**기준치를 넘지 못하면 채택하지 않는다.** 속도는 품질을 이기는 근거가 되지 못한다.
비용은 병목이 아니다 — 전체 재적재 1회가 약 4원, 실험 10회를 해도 40원 수준이다.

### 배운 것
도구는 "문법이 맞는가"만 보고 "뜻이 맞는가"는 보지 못한다. 이번 작업 중에만
컴파일을 통과한 잘못된 코드가 세 번 나왔다.

- `client.scroll(...)` — `...` 은 실제 파이썬 객체라 문법 오류가 아니다
- `headers={...}` 를 독립된 문장으로 나열 — 요청을 보내는 줄이 없는데 전부 합법
- `[___["embedding"] for ___ in ...]` — `___` 은 합법적인 변수 이름이다

셋 다 컴파일 OK 였다. 이 프로젝트에서 반복해서 확인한 교훈이 또 나왔다.
**계측 도구가 통과시켰다는 것은 아무것도 보장하지 않는다.**

### 변경 사항
- `config.py` — `embed_provider` / `embed_api_key` / `embed_api_url` / `embed_cloud_model` 추가
- `repositories/vector_repository.py` — `_embed()` 를 분배자로 분리, `_embed_cloud()` 신설
- `repositories/vector_repository.py` — `similarity_search()` 안의 도달 불가 코드 제거

## v4.11 — top_k 스윕: 검색 지표와 답변 지표는 반대로 움직인다

### 배경
유일하게 남은 검색 실패(`계약만료`)를 고치려 했다. 반사적으로 떠오르는 답은 하이브리드 검색
(키워드+벡터)이었지만, **만들기 전에 이 케이스에 맞는지 확인**했다.

```
정답 청크(#3) 전체 순위 : 10등 / 136   거리 0.605 (1등 0.541)
질문의 단어 : 이전 · 직장을 · 그만둔 · 이유가 · 무엇인가요
정답의 단어 : 퇴사사유 · 계약만료 · 근무지역 · 서울시청 ...
겹치는 단어 : 0개
```

**질문과 정답이 단어를 하나도 공유하지 않는다.** BM25 를 붙여도 이 케이스는 그대로 실패한다.
"RAG 개선하면 하이브리드 검색"은 거의 반사적으로 나오는 답이지만, 우리 실패 사례에는 맞지 않았다.
**일반론이 내 문제에 맞는지 먼저 확인해야 한다.**

정답이 10등이므로 `top_k` 를 늘리면 확실히 잡힌다. 코드를 쓰지 않고 실험할 수 있어 이것부터 쟀다.

### 결과

| top_k | Recall | MRR | 답변 정확도 | 과잉 거절 | 환각 |
|---|---|---|---|---|---|
| **4** | 94.4% | 0.815 | **13/18 (72.2%)** | 2/18 | **1/4 (25%)** |
| 8 | 94.4% | 0.815 | 13/18 (72.2%) | 1/18 | 1/4 (25%) |
| 10 | **100%** | 0.820 | 8/18 (44.4%) | **0/18** | **4/4 (100%)** |

`top_k=10` 은 **검색 지표가 전부 최고점**이다. Recall 100%, 문서 적중 100%, 과잉 거절 0건.
검색만 재는 시스템이었다면 "완벽하게 개선했다"고 결론 냈을 것이다.

그런데 **답이 없는 질문 4개에 전부 답을 지어냈다(25% → 100%).**
답변 정확도도 13/18 에서 8/18 로 떨어졌다.

### 왜 그런가
`top_k` 를 늘리면 LLM 앞에 **뭐라도 그럴듯해 보이는 조각**이 늘 하나쯤 놓인다.
그러면 "근거가 없으면 거절하라"는 규칙이 발동할 기회를 잃는다. LLM 입장에선 근거가 있어 보이기 때문이다.
**거절 능력과 검색 범위는 반비례한다.**

### 결정 — `top_k = 4` 유지
`계약만료` 하나를 더 맞히려고 환각률을 4배로 올릴 수는 없다. 검색 실패는 "모르겠습니다"로 끝나지만,
환각은 사용자가 틀린 답을 믿고 행동하게 만든다(v4.10 의 `50 cm → 15 cm` 사례).

`top_k=8` 은 과잉 거절이 1건 줄지만 답변 정확도는 동일하고 컨텍스트는 2배(2,000 → 4,000자)다.
얻는 것에 비해 비용이 커서 채택하지 않았다.

### 배운 것
**검색 지표와 답변 지표는 반대 방향으로 움직일 수 있다.** 한 층만 재는 평가 체계는 이 함정에
그대로 빠진다. v4.10 에서 답변 평가를 만들어두지 않았다면 `top_k=10` 으로 바꾸고
"Recall 100% 달성"이라고 좋아했을 것이다.

또한 v4.9 에서 청크 크기로 배운 **"많이 주는 것이 잘 주는 것이 아니다"** 가 `top_k` 에서도
똑같이 성립했다. 컨텍스트 양은 늘릴수록 좋은 것이 아니다.

### 변경 사항
- `evals/run_answer_eval.py` — `--top-k` 인자 추가 (기존에는 4 고정)
- `evals/reload_corpus.py` — 업로드 청크 수가 `?` 로 출력되던 문제 수정
  (SSE 이벤트마다 담긴 필드가 달라 마지막 이벤트만 보면 놓친다)
- 운영 설정은 바꾸지 않았다. `top_k: 4` 유지.

### `계약만료` 는 여전히 미해결
효과가 있을 후보는 두 가지로 좁혀졌다.
- **질문 재작성(query rewriting)** — "그만둔 이유"를 "퇴사 사유"로 LLM 이 변환해 재검색.
  어휘 격차를 직접 해결하지만 **검색마다 LLM 호출**이 붙어 53ms 가 수 초가 된다.
- **재순위(rerank)** — 질문과 청크를 함께 읽는 모델. 정답이 10등이므로 상위 20개를 재정렬하면 유망하다.

근본 원인은 v4.10 과 같다. 해당 청크가 와이즈넛 경력 · 서울시청 경력 · 경력기술서 시작을
한꺼번에 담은 뒤범벅이라는 것이다.

## v4.10 — 답변 단계 평가 도입 + PDF 추출 방식 결판(setSortByPosition)

### 추가 — 답변 단계 평가 (`evals/run_answer_eval.py`)
검색만 재던 평가에 마지막 단계를 붙였다. 정답 청크를 가져와도 LLM 이 못 읽거나
엉뚱한 조각을 갖다 붙이는 실패가 있다. 반대 방향인 두 실패를 함께 센다.

- **과잉 거절** — 문서에 답이 있는데 "찾을 수 없습니다"라고 한다
- **환각** — 문서에 답이 없는데 그럴듯한 답을 만들어낸다

한쪽만 보고 조이면 다른 쪽이 나빠지므로 같이 재야 한다.

- `evals/dataset_negative.json` — 답이 없어야 하는 질문 4개(원문 대조로 부재 확인)
- `evals/reload_corpus.py` — 문서 삭제 후 재업로드 자동화. 실험 1회가 손으로 4단계에서
  명령 한 줄로 줄었다. 이 덕분에 아래 A/B 를 실제로 돌릴 수 있었다.

### 결판 — `setSortByPosition` 은 `true` 가 맞다
9월 16일에 추출된 텍스트를 **눈으로 보고** "다단 매뉴얼에는 `false` 가 낫다"고 판단하고
검증을 미뤄뒀다. 같은 문서·같은 평가셋(18문항)으로 끝까지 재보니 반대였다.

| | **true** | false |
|---|---|---|
| Recall@4 | **94.4%** | 77.8% |
| MRR@4 | **0.815** | 0.634 |
| 문서 적중@4 | 100% | 100% |
| 답변 정확도 | **13/18** | 8/18 |
| 과잉 거절 | **2/18** | 5/18 |
| 환각 | 1/4 | 1/4 |
| 가이드 청크 수 | 122 | 118 |

`false` 에서는 **거절이 아니라 틀린 숫자를 자신 있게 답하는** 사례가 나왔다.
"화면과 눈의 거리"를 물었을 때 `50 cm`(정답) 대신 `15 cm`(통풍구·심장박동 보조장치

**배운 것: 사람 눈에 읽기 좋은 텍스트와 검색·LLM 이 다루기 좋은 텍스트는 같지 않다.**
인상으로 판단하지 말고 끝까지 측정해야 한다. 근거 수치를 코드 주석에 남겼다.

### 거리 임계값으로 "모르겠다"를 판정하는 방법은 쓸 수 없다
답이 있는 질문과 없는 질문의 top-1 거리가 겹친다.

```
답 있음 : 0.286 ~ 0.574  (평균 0.428)
답 없음 : 0.439 ~ 0.577  (평균 0.517)
```

0.50 에서 자르면 답 없는 4/6 을 잡는 대신 **답 있는 4/16 을 잘못 버린다.**
거리 스케일이 문서마다 다르기 때문이다 — 표 형식인 이력서 질문은 거리가 전반적으로
크고(0.52~0.57), 설명문인 가이드 질문은 작다(0.29~0.41). 절대 기준은 성립하지 않는다.

그리고 **위험한 것은 무관한 질문이 아니라 "그럴듯한데 문서엔 없는" 질문**이었다.
노트북 가격(0.439)과 환불 정책(0.449)이 김치찌개(0.573)보다 가까웠다.

현실적인 방어는 프롬프트 규칙이고, 실제로 작동한다(무관한 질문 3/4 거절).
다만 **문서에 있는 조각을 엉뚱한 질문의 답으로 쓰는 환각은 막지 못한다.**
"희망 근무 지역?" → "경기입니다"(실제로는 과거 재직지)가 그 예다.

### 채점기 버그 — 눈에 보이지 않는 공백
LLM 이 `50 cm` 의 공백으로 `U+202F`(NARROW NO-BREAK SPACE) 를 써서, 정답인 답변이
오답으로 집계됐다. 화면에는 보통 공백과 똑같이 보인다.
두 스크립트에 NFKC 정규화 + 공백 접기(`normalize()`)를 추가했다.
**이 프로젝트에서 측정 도구가 거짓말한 네 번째 사례다.**

### 평가셋 라벨 오류 2건 정정
`환불 정책`과 `퇴사 사유`를 "답 없는 질문"으로 분류했으나 원문 대조 결과 둘 다 있었다
(가이드 #118/#119 의 교환/환불, 이력서 #3 의 `퇴사사유 계약만료`). 정식 질문으로 옮겼다.
**평가셋은 코드보다 검증이 더 필요하다** — 틀려도 에러가 나지 않고 조용히 잘못된 숫자를 낸다.

### 답변 단계 채점의 한계 (알고 쓰기)
문자열 포함 방식은 검색 채점에는 잘 맞지만(청크는 원문 그대로) 답변 채점에는 약하다.
- `구입처` 를 기대했는데 LLM 이 `구매처` 로 바꿔 씀 → 정답인데 오답 집계
- 검색이 못 가져온 질문은 LLM 이 거절하는 게 옳은데 "과잉 거절"로 집계됨

따라서 `답변 정확도 72.2%` 는 실제 품질을 **과소평가**한다.
숫자는 추세 비교용으로 쓰고, **실패 목록은 눈으로 읽는다**(18문항이면 1분이면 된다).

## v4.9 — 청크 크기 500으로 정정 (MRR 0.688 → 0.854) + MRR 지표 도입

### v4.8 정정: 350 은 성급한 결론이었다
v4.8 에서 `chunk-size` 를 700 → 350 으로 바꾸며 "Recall@4 75% → 100%" 를 근거로 삼았다.
그런데 **Recall@4 가 100% 에 닿은 순간 그 지표로는 더 이상 우열을 가릴 수 없었다.**
"더 볼 게 없다" 가 아니라 "이 자로는 더 못 잰다" 였는데 그대로 결정해버렸다.

순위를 반영하는 MRR 을 추가하고 500 을 재보니 350 보다 뚜렷하게 나았다.

| | 700 | 350 | **500** |
|---|---|---|---|
| Recall@4 | 75% | 100% | **100%** |
| MRR@4 | 0.667 | 0.688 | **0.854** |
| 1등으로 찾은 개수 | 10 | 7 | **12** |
| 최악 순위 | 20등 밖 | 3등 | 3등 |
| LLM 컨텍스트 | 2,800자 | 1,400자 | 2,000자 |
| 가이드 업로드 임베딩 | 73.6s(IPv6 수정 전) | 80.2s | **63.7s** |
| 가이드 청크 수 | 80 | 200 | 122 |

350 대비 MRR 이 0.688 → 0.854 로 오르고 **업로드도 20% 빨라졌다**(80.2s → 63.7s,
둘 다 IPv6 수정 이후 값이라 비교 가능). 700 의 업로드 수치는 수정 이전이라 직접 비교할 수 없다.

### 변경 사항
- `application.yml` — `document.chunk-size: 350` → **500**
- `evals/run_eval.py` — MRR@k 출력 추가 (순위의 역수를 평균)

### MRR 을 왜 도입했나
정답 순위를 점수로 환산한다. 1등 1.000 / 2등 0.500 / 3등 0.333 / 4등 0.250 / 못 찾으면 0.
**천장이 없어 미세한 변화를 감지한다.**

다만 우리 시스템은 상위 k개를 전부 LLM 에 넘기므로, 정답이 1등이든 4등이든 LLM 입장에서는
같다. 따라서 **성과 지표는 Recall@4 이고, MRR 은 진단 지표**로 쓴다.
실제로 700 → 350 변화를 MRR 로 분해하니 공짜 개선이 아니라 거래였다는 것이 드러났다.

- 못 찾던 4개를 찾게 됨 (0 → 0.33~0.5)
- 1등이던 4개가 2등으로 밀림 (1.0 → 0.5)
- 합계 +0.021 뿐 — Recall 의 +25%p 는 개선 폭을 과장하고 있었다

### 통계적 신뢰도에 대한 단서
평가셋이 16문항뿐이므로 솔직하게 적어둔다.
- `0.688 vs 0.667` (350 vs 700) — 항목 하나로 뒤집히는 차이. 우연일 가능성이 높다.
- `0.854 vs 0.688` (500 vs 350) — 1등이 7개에서 12개로. 실제 차이로 볼 만하다.

따라서 결론은 **"500 이 정확한 최적값"** 이 아니라 **"500 근처가 350·700 보다 낫다"** 이다.

### 배운 것
- **천장에 부딪힌 지표로 결정하지 말 것.** 100% 가 나오면 축하할 일이 아니라 자를 바꿀 신호다.
- **첫 개선에서 멈추지 말 것.** 700 → 350 에서 만족했다면 더 나은 500 을 놓쳤을 것이다.
- 이 프로젝트의 두 번째 정정이다(첫 번째는 v4.7 의 "임베딩 97.9%"). 둘 다 측정을 더 잘하게
  되자 뒤집혔다. 결론이 바뀌는 것은 측정 체계가 살아 있다는 뜻이다.

## v4.8 — 청크 크기 700 → 350 (Recall@4 75% → 100%, 컨텍스트 절반)

### 배경
v4.7 에서 만든 평가셋이 너무 쉬워 100% 가 나왔다. 문서 간 혼동을 유도하는 질문을 넣고
`expect` 를 원문 실재 문자열로 바로잡자 **Recall@4 가 75% 로 떨어졌다**(16문항 중 4개 실패).

### 진단 — 실패는 "문서"가 아니라 "청크" 문제였다
문서 적중률은 16/16 = 100% 를 유지했다. 즉 맞는 문서를 가져오면서 그 안의 엉뚱한 청크를 골랐다.
`top_k` 를 올려 실패를 두 종류로 분리했다.

```
Recall@4  75.0%   →  @8  87.5%  →  @20 87.5%  →  @89 100%
```

- **순위 문제 2개** — 정답이 6등. 후보를 늘리면 잡힌다.
- **인식 문제 2개** — 정답이 20등 밖. `top_k` 를 늘려도 올라오지 않았다.

인식 문제 두 개의 정답(`root-context.xml`, `netstat`)이 **같은 청크(이력서 #0)** 에 있었다.
그 청크 하나에 이름·연락처·학력·회사·기술스택·보안 유지보수·인프라 관리가 모두 들어 있었다.
임베딩은 청크 전체를 하나의 좌표로 요약하므로, 주제가 여섯 개 섞이면 그 좌표는 어느 주제의 중심도
아닌 지점에 놓인다. 그래서 "서비스 포트 점검 도구"라고 콕 집어 물어도 닮은 청크로 인식되지 않았다.

### 변경 사항
- `application.yml` — `document.chunk-size: 700` → **350** (`chunk-overlap` 은 100 유지)

### 결과 (같은 문서, 같은 평가셋)

| | chunk 700 | chunk 350 |
|---|---|---|
| Recall@4 | 12/16 (75.0%) | **16/16 (100.0%)** |
| 문서 적중@4 | 16/16 | 16/16 |
| 최악 순위 | 20등 밖 | **3등** |
| LLM 에 넘기는 글자 수 | 4 × 700 = 2,800자 | **4 × 350 = 1,400자** |
| 검색 시간 | 63ms | 60ms |
| 가이드 업로드 임베딩 | 73,599ms (80청크) | 80,239ms (200청크) |
| 임베딩할 총 글자 수 | 약 59,000자 | 72,641자 |

20등 밖이던 두 질문이 **2등**으로 올라왔다.

### 배운 것
- **컨텍스트를 절반으로 줄이면서 정확도가 올랐다.** 큰 청크는 관련 있는 내용과 없는 내용을 같이
  실어 나른다. "많이 주는 것"이 "잘 주는 것"이 아니다. 토큰 비용·답변 속도·LLM 혼란 여지가 함께 줄었다.
- **검색 품질은 검색 알고리즘보다 청킹에서 결정되는 경우가 많다.** 알고리즘은 한 줄도 바꾸지 않았다.
- 지표를 Recall 과 문서 적중률 **두 개로 나눠 잰 것이 진단을 가능하게 했다.** Recall 만 봤다면
  "검색이 나쁘다"에서 멈췄을 것이다.
- 대가는 업로드 +9%(약 7초)뿐이었다. 글자 수는 +23% 늘었지만 배치 처리로 호출당 고정비용이 분산됐다.
  v4.7 의 IPv6 수정이 없었다면 배치가 5→13개로 늘어 약 17초가 더 붙었을 것이다.

### 남은 한계
`Recall@4` 가 100% 에 닿아 **더 이상 개선을 구분할 수 없다.** 350 이 최적인지, 그냥 700보다
나은 것인지 알 방법이 없다. 순위를 반영하는 연속 지표(MRR)가 필요하다.

127.0.0.1 로 Ollama 호출 :   39ms,   46ms,   37ms

원인: Ollama(11434)와 FastAPI(8001)는 **127.0.0.1 에만 바인딩**돼 있는데, `localhost` 는 `::1`(IPv6) 로 먼저 해석된다.
매 요청이 IPv6 로 연결을 시도하다 실패하고, 약 2초 뒤 IPv4 로 폴백했다. 코드·모델·DB 모두 정상이었다.

**조치**: 기본 주소를 `127.0.0.1` 로 변경 — `config.py` 의 `ollama_base_url`, `application.yml` 의 `ai.service.url`, `evals/run_eval.py` 의 `AI_URL`.
(브라우저가 쓰는 주소는 `localhost` 유지 — 브라우저는 IPv6 실패를 빠르게 처리한다.)

**결과**

| | 전 | 후 |
|---|---|---|
| 검색 전체 | 4,485ms | **53ms** (85배) |
| 쿼리 임베딩 | 2,076ms | 41ms |

### 배운 것 — 이 100%를 믿으면 안 되는 이유
- 처음 만든 가이드 6문항은 **검색 결과를 본 뒤에 만든 질문**이었다(평가셋 오염). 이력서 4문항은 문서를 보지 않고 질문을 먼저 쓴 뒤 본문에서 단어를 골라 오염을 줄였다.
- `expect` 를 한 문서에만 있는 고유명사로 잡으면 문제가 쉬워진다. 실제로 양쪽 문서에 모두 흔한 단어로 물었을 때는 실패했다:
  "삼성 관련 경험이 있나요?" → 상위 4개가 **전부 갤럭시북 가이드**. 이력서를 전혀 가져오지 못했다.
- 즉 현재 100%는 **출발점이지 목표가 아니다.** 다음 단계는 문서 간 혼동을 유도하는 질문을 평가셋에 넣는 것.

## v4.6 — 잔여 벡터(정합성 깨짐) 예방·감지·회복

### 배경
- `DocumentService.upload()` 은 **벡터를 먼저 저장하고(`embedAndStore`) 문서 메타데이터를 나중에 저장**(`documentRepository.save`)했다.
  그 사이에서 예외가 나거나 프로세스가 죽으면 **Qdrant에는 벡터가 있는데 H2에는 문서가 없는** 상태가 남는다.
- `similarity_search` 는 컬렉션 전체를 대상으로 하므로, 주인 없는 벡터도 검색 결과와 LLM 컨텍스트에 섞여 들어간다.
  청크 수가 `full_context_threshold` 이하면 `scroll` 로 **전부** LLM에 전달되므로 영향이 더 크다.
- 실측: Qdrant `doc_id` 2건 vs H2 문서 0건. 화면 목록은 비어 있는데 검색은 답을 내놓는 상태였다.

### 변경 사항

**예방 — 보상 트랜잭션**
- `DocumentService.upload()` 의 `embedAndStore` 를 `try/catch` 로 감싸고, 실패 시 `cleanupLeftoverVectors(docId)` 로 방금 저장한 벡터를 삭제한 뒤 원래 예외를 그대로 재던진다(`throw e`).
- 정리 자체가 실패해도 원래 예외를 덮지 않도록 헬퍼 내부에서 다시 `try/catch` 하고 로그만 남긴다.

**감지 — 시작 시 정합성 점검**
- `@EventListener(ApplicationReadyEvent.class) checkLeftoversOnStartup()` — 앱이 완전히 뜬 뒤 Qdrant/H2 차집합을 계산해 **경고만** 남긴다. 자동 삭제는 하지 않는다.
- AI 서비스가 아직 안 떠 있어도 스프링 기동을 막지 않도록 전체를 `try/catch` 로 감쌌다.

**회복 — 명시적 정리 API**
- `GET  /api/documents/leftovers` — 삭제 없이 조회만
- `POST /api/documents/cleanup` — 실제 삭제, 삭제 건수 반환
- 삭제는 되돌릴 수 없으므로 **감지와 실행을 분리**했다.

**Backend (AI)**
- `vector_repository.list_doc_ids()` — `scroll` 페이지네이션으로 전체를 훑어 중복 제거된 `doc_id` 목록 반환. `with_vectors=False` 로 1024차원 벡터는 받지 않는다.
- `GET /ai/documents/doc-ids` 라우터 추가 (변수 경로 `/{doc_id}` 보다 위에 배치)

### 검증
- **결함 주입(fault injection)**: `embedAndStore` 직후에 임시로 `RuntimeException` 을 던져 실패 경로를 강제 실행.
  로그에서 `잔여 벡터 정리 완료` → `업로드 처리 실패` 순서를 확인해 **정리 후 원래 예외가 살아서 전파되는 것**까지 증명했다. 확인 후 주입 코드는 제거.
- 실제 잔여 벡터 2건을 감지 → 조회 → 정리 → 재조회(`count: 0`)까지 전 과정 로그로 확인.

### 배운 것
- `h2:file:` 인 것을 먼저 확인했다. `h2:mem:` 이었다면 재시작마다 H2가 비므로 "H2에 없는 벡터를 지운다"는 로직이 **Qdrant를 통째로 삭제**했을 것이다. 삭제 로직은 판단 기준이 되는 데이터가 비어 있을 수 있는지를 먼저 의심해야 한다.
- 실행 중인 JVM은 시작 시점의 클래스를 들고 있다. 소스를 고쳐도 **재시작 전까지 반영되지 않는다**.
- 서비스 간 경로는 문자열이라 컴파일러가 검사해주지 않는다(`/docids` 오타 → 404). 마이크로서비스의 구조적 비용.

## v4.5 — 단계별 소요 시간 계측 + 청킹 버그 수정 (backend-spring 첫 테스트)

### 배경
- v4.4 의 요청 로깅으로 "업로드가 느리다"는 건 알았지만 **어느 단계가** 느린지는 몰랐음.
  SSE 때문에 필터가 재는 시간(40~63ms)이 실제 소요 시간(11~17초)과 무관했기 때문
- 감으로 최적화하면 전체의 3% 짜리(PDF 추출)를 붙잡을 위험이 있었음

### 변경 사항
- `DocumentService.upload()` 에 단계별 계측: `extract / split / embed / total`
- `vector_repository.add_chunks_stream()` 에 `embed / upsert` 분리 계측
- `splitText` 를 `static` + 파라미터(`chunkSize`, `chunkOverlap`) 방식으로 변경 —
  필드 의존을 없애 **순수 함수**로 만들어 단위 테스트가 가능해짐
- **버그 수정**: 청크 사이 겹침(overlap)을 이어붙일 때 `chunkSize` 초과 여부를 검사하지 않아,
  긴 줄이 들어오면 청크가 `chunkSize + chunkOverlap + 1` 까지 커졌음
  (700 설정에서 **751자** 관측). 겹침을 붙여도 한도를 넘지 않을 때만 붙이도록 수정 —
  문장을 중간에서 자르는 대신 겹침을 포기하는 쪽을 택함
- `src/test/java/com/ragsearch/service/DocumentServiceSplitTextTest` 신규 —
  **backend-spring 최초의 테스트**. 실행: `cd backend-spring; mvn test`

### 측정 결과 (9청크 PDF 업로드)
```
Java   : extract 135ms, split 6ms, embed 11144ms, total 11285ms
Python : embed 11053ms, upsert 52ms, total 11107ms
```
- **임베딩이 전체의 97.9%.** Qdrant 저장 52ms(0.5%), Spring↔FastAPI 통신 37ms
- `bge-m3` 가 100% CPU 로 도는 환경(GPU 없음)이라 소프트웨어 최적화 여지가 거의 없음 →
  실질적 선택지는 **GPU 데스크탑** 또는 **클라우드 임베딩 API**(배포 시 어차피 필요)
- 벤치마크 교훈: 처음엔 `"가".repeat(500)` 으로 측정했는데 반복 문자는 토큰이 훨씬 적게 나와
  실제보다 빠르게 측정됨. **실제 데이터로 재야 한다**

### 정정 — "청크가 설정값의 2배" 는 코드 버그가 아니라 **측정 오류**였음
조사 중 "Qdrant 에 저장된 청크가 평균 1,362자(최대 1,663자)" 로 관측되어 `splitText` 의
이론적 상한(801자)을 넘는 것처럼 보였으나, **검증 결과 저장된 청크는 최대 699자로 정상**이었다.

원인은 코드가 아니라 조회에 쓴 도구였다. PowerShell 5.1 의 `Invoke-WebRequest` 가 UTF-8
응답을 Latin-1 로 디코딩하면서 **한글 1자(UTF-8 3바이트)가 깨진 글자 3개로 늘어나** 문자열
길이가 ~2.5배로 부풀었다.

```
Java 로그            : 80 chunks, textLen 47611, longest 699
PowerShell 기본 디코딩 : 최대 1663, 평균 1499   ← 부풀려진 값
UTF-8 강제 디코딩      : 최대  699, 평균  670   ← Java 와 일치
```

- 올바른 조회 방법: `[System.Text.Encoding]::UTF8.GetString($resp.RawContentStream.ToArray())`
- **교훈**: "저장된 청크의 최소값(739)이 생성된 청크의 최대값(699)보다 크다"는 논리적으로
  불가능한 값이었다. 이런 값이 나오면 **코드보다 계측을 먼저 의심**해야 한다.
  같은 응답의 파일명이 `ì¬ëì¸_...` 로 깨져 있었던 것이 이미 단서였다
- 이 프로젝트에서 인코딩 문제는 네 번째다 (PowerShell BOM, 자바 로그 CP949,
  `PYTHONUTF8`, 그리고 이번 조회 디코딩) — 한글 프로젝트의 고질적 함정
- 참고: 위의 **겹침(overlap) 버그(751자)는 실재한다.** 그건 PowerShell 이 아니라
  JUnit 테스트로 JVM 안에서 직접 측정해 인코딩 계층이 개입하지 않았다

### 남은 과제
- **고아 벡터**: `embedAndStore`(벡터 저장) 이후 `documentRepository.save`(문서 등록) 전에
  업로드가 끊기면 벡터만 남고 문서 기록이 없어짐. 관측 시점 기준 Qdrant 73청크 vs H2 1문서
  (이 수치는 개수 집계라 인코딩 문제와 무관하며 유효함).
  `similarity_search` 는 컬렉션 전체를 뒤지므로 **삭제된 문서가 답변 근거로 계속 쓰임**

## v4.4 — 개발용 요청 로깅 + VS Code 디버그 환경

### 배경
- 계층이 4개(React → Spring → FastAPI → Ollama)인데 **Spring 계층만 요청 로그가 없어서**,
  요청이 어디까지 갔는지 확인할 방법이 없었음. FastAPI 는 uvicorn access log 가 있고,
  React 는 브라우저 Network 탭이 있는데 가운데만 깜깜했음
- SSE 스트리밍 중 브라우저가 "생성중"에서 멈추는 현상을 디버깅할 때, Spring 로그를
  직접 뒤져서야 원인(`IllegalStateException: response object has been recycled`)을 찾을 수 있었음
- 앞으로 검색·임베딩 속도를 개선하려면 **"얼마나 걸리는지" 측정 수단이 먼저** 필요

### 변경 사항
- `config/RequestLoggingFilter` 신규 (`OncePerRequestFilter`):
  `METHOD /path -> status (Xms)` 형태로 모든 요청 로깅. `try/finally` 로 실패한 요청도 남김
- `application.yml` 에 `logging.file.name: logs/spring.log` 추가 — 콘솔 설정
  (integratedTerminal / internalConsole)에 좌우되지 않고 **항상 파일로** 남도록.
  실시간 확인: `Get-Content backend-spring\logs\spring.log -Wait -Tail 5`
- `.vscode/launch.json` 에 "Spring Boot" 자바 디버그 설정 추가.
  `vmArgs` 에 `-Dfile.encoding=UTF-8 -Dsun.jnu.encoding=UTF-8` 필수 (없으면 한글 깨짐)

### 알아낸 것
- **SSE 엔드포인트의 시간은 이 필터로 못 잰다.** `upload()` 가 `SseEmitter` 를 반환하는 순간
  요청이 비동기로 전환되어 원래 스레드가 즉시 반환되므로, 업로드가 `63ms` 로 찍힌다.
  실제 작업(추출→청킹→임베딩)은 그 뒤 `sseExecutor` 스레드에서 진행됨.
  `request.isAsyncStarted()` 로 `[async]` 표시를 붙여 이 숫자를 믿지 않도록 표시함.
  **진짜 소요 시간 측정은 별도 과제** (서비스 내부 측정 또는 `AsyncListener`)
- 로그 메시지는 **ASCII 로** 작성할 것. Java 가 UTF-8 로 쓰는데 Windows 터미널이 CP949 로
  읽으면 한글이 깨진다. 배포 환경(Docker/클라우드 로그 뷰어)까지 고려하면 ASCII 가 안전
- PDF 추출 품질: 디버거로 `DocumentService.extractText()` 결과를 직접 확인한 결과,
  `setSortByPosition(true)` 는 다단 레이아웃 문서(삼성 노트북 설명서, 47,611자)에서
  **단을 가로질러 읽어 문장을 쪼갠다** ("데이터를 백업해" + 다른 단 내용 + "두세요.").
  `false` 로 두면 순서가 보존됨. 다만 주석에 적힌 "이력서·양식 문서엔 `true` 가 낫다"는
  주장은 아직 검증 전이라 `true` 유지 — **이력서 PDF 로 같은 실험을 하는 것이 남은 과제**

## v4.1 — RAG 품질/인코딩 디버깅 (한국어 문서)

### 증상
- 답변 품질이 낮고 환각이 심함, 응답이 느림 (이력서 PDF 기준)

### 원인 및 조치

**1. 한국어 깨짐 (MS949) — 가장 큰 원인**
- 한국어 Windows 에서 JVM `file.encoding=MS949` → AI 서비스의 UTF-8 응답(SSE),
  업로드 텍스트 파일, 멀티파트 파일명이 전부 깨져서 LLM 에 gibberish 컨텍스트가 들어감
- `pom.xml` spring-boot-maven-plugin 에 `-Dfile.encoding=UTF-8 -Dsun.jnu.encoding=UTF-8`
- `AiServiceClient`: `InputStreamReader` 에 `StandardCharsets.UTF_8` 명시 (2곳)
- `DocumentService.extractText`: `new String(bytes, UTF_8)`
- `Dockerfile`: JDK 20→17, `ENTRYPOINT` 에 UTF-8 플래그

**2. 임베딩 모델이 한국어에서 사실상 무작위**
- `nomic-embed-text` 는 영어 위주 → 한국어 쿼리·청크 유사도가 거의 구분 안 됨
  (검증: 청크에 그대로 들어있는 문장을 쿼리해도 top-8 밖)
- → `bge-m3` (다국어, 1024d) 로 교체. 동일 쿼리에서 정답 청크가 명확한 마진으로 1위

**3. 청킹이 문장 중간을 자름**
- 고정 500자 슬라이딩 → 줄 단위로 모아 700자까지 채우는 방식으로 변경 (`splitText`)
- 이력서·표처럼 줄 구조가 의미를 갖는 문서에서 청크 경계가 자연스러워짐

**4. 다단(컬럼) PDF 추출 순서 엉킴**
- `PDFTextStripper.setSortByPosition(true)` — 좌→우, 상→하 순서로 추출

**5. LLM**
- `llama3.2:3b` → `qwen2.5:3b` (한국어 품질·속도 모두 우위, ~12 tok/s)
- 프롬프트에 간결성 규칙 추가, `num_predict` 1024→640, `top_k` 6→4

### 남은 한계 (하드웨어)
- 이 PC: Intel Ultra 5 125H, 16GB, 디스크리트 GPU 없음 → Ollama 100% CPU
- bge-m3(1.2GB) + qwen2.5:3b(2.2GB) 동시 로드 시 RAM 여유 부족 → 스와핑 → 응답 지연 편차 큼

### 6. LLM provider 선택 + 소규모 문서 full-context (v4.1 후속)
- `LLM_PROVIDER=ollama|groq` — 임베딩·벡터는 계속 로컬, 답변 생성만 Groq 클라우드로 오프로드 가능
  - `_stream_ollama` / `_stream_groq` 분기, SSE 계약 동일
  - 기본 모델 `openai/gpt-oss-120b`. gpt-oss 계열은 `reasoning_effort=low` 로 과잉 추론 억제
    (안 하면 단답에도 10~17초). 적용 후 이력서 6질문 평균 3.1초 (Ollama CPU 는 25~70초)
  - Groq 모델 목록이 자주 바뀜 — `llama-3.3-70b-versatile` 등 구 모델은 404. 콘솔에서 확인
- `FULL_CONTEXT_THRESHOLD` (기본 12) — 컬렉션 청크 수가 이하이면 벡터 검색을 건너뛰고
  전체 청크를 순서대로 컨텍스트에 넣는다. 문서 1~2개짜리 데모에서 검색 누락 제거
